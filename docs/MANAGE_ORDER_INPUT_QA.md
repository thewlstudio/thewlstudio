# 순서 변경 입력·조회 목록 점검

## 확인한 문제

- `Array.every`가 빈 슬롯을 건너뛰어 잘못된 요청이나 조회 목록이 다음 단계까지 들어갔다. 모의 테스트에서 문서 조회 후 TypeError가 발생하거나 트랜잭션 객체를 만든 뒤 예외가 발생했다. 운영 커밋이 발생한 것으로 확인한 것은 아니다.
- 조회 행의 배열 여부·자체 문서 ID/버전·공백 버전을 충분히 확인하지 않았다. 숫자가 아닌 순서값도 정상 숫자로 추측해 덮어쓸 수 있었다.
- 중복 요청 ID는 조회 후 거부했으며, 중복 원본 ID도 일반 목록 불일치로만 거부했다. 이제 각 입력 경계에서 명시적으로 검사한다.
- 그룹의 공백 문자열·상속 속성도 그룹 정보로 통과했다.
- 최소 순서값을 `Math.min(...values)`로 구해 큰 합성 목록에서는 함수 인자 수 제한으로 실패했다. 현재 운영 규모에서 발생한 문제는 아니다.

## 반영 내용

- 드래그 ID 배열은 자체 인덱스가 빠짐없이 있어야 하며, 공개 문서 ID 형식과 중복 여부를 조회 전에 검사한다. 인증은 기존 서버 액션에서 먼저 수행한다.
- 조회 목록은 자체 인덱스·객체 행·고유한 공개 ID·자체 비공백 버전을 검사한다. 잘못된 행을 제외해 일부 목록만 저장하거나 버전 정보를 새로 만들어 쓰지 않는다.
- 순서 필드는 누락·undefined·null·숫자만 허용한다. 문자열·불리언·객체·배열·상속 값은 자동 변환하지 않고 원본 확인/새로고침을 안내한다. 숫자의 중복·소수·NaN/Infinity·안전 범위 초과를 연속 정수로 정리하던 기존 계약은 유지한다.
- 그룹 정렬은 자체 비공백 문자열 그룹만 사용하고, 그룹 문자열을 임의로 다듬거나 다른 종류 사이 이동을 허용하지 않는다. 최솟값 계산은 반복문으로 바꿨다.
- 검증 실패 시 트랜잭션 생성·커밋·성공 후 캐시 갱신을 하지 않는다. 정상적인 변경 항목만 패치·revision 조건·그룹별 정규화 범위·원본 불변성은 유지한다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽고 서버 함수 입력 검증 원칙을 확인했다. 페이지 디자인·스키마·환경변수·의존성은 변경하지 않았다.

## 검증

새 테스트 **105개**를 추가했다.

- 공통 함수 60개: 드래그/화살표의 비정상 원본 19종, 잘못된 요청 8종, 그룹 원본 6종, 정상 숫자/누락 순서 정리·원본 불변성 7종, 15만 행 합성 목록의 무변경 처리 1종.
- 실제 서버 액션 45개: 여섯 순서 변경 경로의 잘못된 원본 6종, 세 드래그 경로의 잘못된 입력 3종. 인증 후 조회/쓰기/캐시 갱신 단계가 어디까지 실행됐는지 확인한다.
- 보완 전 공통 함수 테스트 25개가 실패하는 것을 재현했고, 보완 후 통과했다. 나머지는 기존 안전 조건과 정상 동작의 회귀 검사다.
- 전체 **4,270개 / 103개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

## 범위와 한계

- CMS·인증은 모의 구현이다. 운영 문서의 순서 변경이나 인증된 브라우저 E2E를 수행하지 않았다. 운영 저장·업로드·커밋·배포도 하지 않았다.
- 원본 ID·버전·순서 자료형 검증이며, 조회한 데이터셋의 완전성을 독립적으로 증명하는 기능은 아니다. 기존 revision 조건은 유지하지만 다른 브라우저/Studio의 모든 동시 추가·삭제·이동을 목록 전체 단위로 직렬화하지 않는다.
- 숫자가 아닌 손상된 원본은 자동 복구하지 않는다. `/admin`에서 원본을 확인해야 한다. 그룹 정렬 시 이동하지 않은 그룹의 숫자 순서값은 기존대로 바꾸지 않는다.
- 큰 목록 테스트는 함수 인자 수 제한 회귀 검사이며 대규모 사이트의 성능 보장을 뜻하지 않는다.
