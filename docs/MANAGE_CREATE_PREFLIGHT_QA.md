# 새 항목 생성 전 주소·정렬값 검증

## 확인한 문제

- Crew·Works의 주소 중복 조회 결과를 숫자로 검증하지 않았다. null·문자열·객체 등 비정상 결과를 중복 없음으로 처리할 수 있었다.
- 강사 생성/복제·Crew 생성·공간 생성에서 순서 응답의 자료형/범위를 확인하지 않고 `Math.max(...orders) + 1`을 계산했다. 문자열 강제 변환·NaN·무한대·안전 정수 초과가 가능했고, 대규모 배열은 인자 펼치기 한계도 있었다.
- 순서가 있는 문서만 읽으므로, 공개 목록에서 기본값 0으로 취급하는 순서 없는 항목이 새 항목 위치 계산에서 빠졌다.
- 일부 생성 경로는 순서 조회와 동시에 또는 그보다 먼저 사진/아이콘을 올렸다. 조회 실패/검증 오류에도 에셋만 먼저 생길 수 있었다.
- 모의 저장소에서 재현한 결함이며 실제 운영에서 잘못된 생성이 발생했다는 뜻은 아니다.

## 반영 내용

- 주소 `count()` 결과는 0 이상의 안전한 정수만 허용한다. 정확히 0일 때만 사용 가능으로 진행한다. 양수이면 기존의 중복 안내, 형식 오류이면 확인 실패 안내를 `slug` 필드에 연결한다.
- 순서는 해당 종류 전체의 `.order` 배열을 읽는다. null은 기존 공개 정렬의 `coalesce(order, 0)`과 같은 기본값 0으로 취급한다. 빈 데이터셋의 첫 값은 기존대로 0이다.
- 순서 응답은 배열이어야 하며 각 값은 null 또는 안전 정수 범위 안의 유한한 숫자여야 한다. 문자열·불리언·undefined·빈 슬롯·NaN·무한대·범위 초과는 거부한다. 다음 안전 정수를 만들 수 없는 상한도 거부한다.
- 예전 소수/음수 순서값은 원본 그대로 유지한다. 새 항목에만 `floor(max) + 1`을 부여해 조회한 최댓값보다 큰 안전한 정수로 만든다. 전체 목록을 재정렬하거나 원본의 중복값을 고치지 않는다. Studio의 전역 순서 계산과 휴지통 포함 범위도 기존대로다.
- 배열을 펼치지 않고 순회한다. 20만 항목도 인자 개수 한계 없이 처리한다.
- 순서 조회와 검증을 대표 사진·배경 사진·선택 사진·Crew 링크 아이콘·공간 사진 업로드보다 먼저 끝낸다. 조회 오류일 때 사진/문서/캐시/성공 이동은 실행하지 않는다.
- 강사 복제는 여전히 원본 사용자 필드를 보존하고 비공개로 생성한다. 인증·필수 입력·기존 미저장 보호·공개 디자인은 변경하지 않았다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽고 적용했다. 설치된 `groq-js`로 `.order` 조회가 누락/null을 `[null, null, ...]`로 보존하는 것도 로컬 데이터로 확인했다.

## 검증

새 테스트 **120개**를 추가했다.

- 실제 생성/복제 액션 117개: 네 순서 경로의 비정상 응답·조회 실패·조회 대기 중 무업로드, 정상/기본/소수/음수/중복/상한 경계, 순서 없는 문서 포함 쿼리, 두 주소 경로의 비정상 중복 개수·이미 쓰는 주소·조회 예외, 강사 복제 비공개/원본 보존.
- 순서 계산 함수 2개: 20만 항목과 빈 슬롯 거부.
- 실제 Studio 생성 폼→액션 1개: 잘못된 순서 조회 응답 때 입력·dirty·서버 원본을 유지하고 업로드/refresh를 실행하지 않음.
- 기존 대상/캐시 테스트의 조회 mock은 변경된 전체 `.order` 쿼리에 맞게 조정했다. 기대 캐시 경로·저장 성공/실패 규칙은 낮추지 않았다.
- 인증·외부 저장소·라우터는 모의 구현이다. 실제 CMS 생성이나 인증된 브라우저 E2E를 대신하지 않는다.

전체 **3,660개 / 97개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

공개 강사 7개·Crew 3개·공간 5개의 순서 배열을 읽기 전용으로 조회해 실제 계산 함수를 메모리에서 실행했다. 거부된 종류 0개였다. Crew/Works 주소 11건의 종류별 중복은 0건이었다. 이는 공개 데이터 시점의 검사이며 초안/릴리스/다른 동시 작성자의 상태까지 검증한 것은 아니다. 원문·문서 ID·인증 정보는 출력하지 않았다.

## 남은 한계

- 주소 조회와 `create()`는 별도 요청이다. 서로 다른 브라우저/Studio가 동시에 같은 주소를 만들면 중복이 생길 수 있다. 같은 탭의 잠금은 유지하지만, 전역 주소 예약 문서·고정 ID 규칙·트랜잭션 예약/해제는 새로 도입하지 않았다.
- 같은 시점에 조회한 생성 요청은 같은 새 순서값을 받을 수 있다. 기존 `_id` 동률 정렬 규칙과 목록 순서 변경 기능은 유지한다. 전역 카운터/동시 편집 프로토콜을 추가한 것은 아니다.
- 검증 이후 실제 업로드 중 연결 실패나 최종 문서 생성 실패가 생기면 이미 올라간 일부 에셋이 남을 수 있다. 자동 에셋 삭제나 원본 재정렬로 복구하지 않는다.
- 운영 저장·실제 업로드·커밋·배포는 하지 않았다. 디자인·스키마·환경변수·의존성도 변경하지 않았다.
