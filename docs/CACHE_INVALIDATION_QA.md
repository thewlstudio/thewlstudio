# 관리자 변경 후 공개 캐시 갱신 점검

## 결론

현재 `/manage` 서버 액션과 공개 조회의 연결을 점검한 범위에서는 **갱신 태그·경로 누락을 발견하지 못했다.** 새 동작 코드를 만들지 않고, 기존 연결을 확인하는 회귀 테스트를 보강했다.

설치된 Next.js 16.4.3의 다음 문서를 모두 읽고 비교했다.

- `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/updateTag.md`
- `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidatePath.md`

현재 구현은 Server Action에서 `updateTag`로 읽기 캐시를 만료시키고, 필요한 페이지·레이아웃·사이트맵 경로에 `revalidatePath`를 호출한다. `revalidateTag(..., "max")`의 백그라운드 갱신 방식으로 바꾸지 않았다.

## 확인한 연결

| 영역 | 공개 조회 태그 | 일반 변경 후 경로 |
| --- | --- | --- |
| 강사 | `instructor` | `/class`, `/manage/instructors` |
| Crew | `crew` | `/crew`, 해당 상세, `/sitemap.xml`, `/manage/crew` |
| Works | `work` | `/works`, 해당 상세, `/sitemap.xml`, `/manage/works` |
| Studio 공간 | `studioSpace` | `/studio`, `/manage/studio` |
| Studio 안내 | `studioInfo` | `/studio` |
| 연락처·공통 설정 | `siteSettings` | `/`의 **layout 전체** |

- Crew 순서 변경은 목록·사이트맵·관리 목록을 갱신한다. 순서 변경에 개별 slug가 필요하지는 않다.
- Works 목록과 페이지 번호별 메타데이터는 같은 `work` 태그의 조회를 사용한다.
- Studio 안내·공통 설정 수정 화면은 `force-dynamic`이며, 저장 성공 후 공통 폼 처리에서 `router.refresh()`를 호출한다. 따라서 일반 저장에 관리 편집 경로의 별도 `revalidatePath`가 없다고 곧바로 누락으로 판단하지 않았다.
- 공통 설정의 루트 layout 갱신은 헤더·본문 링크뿐 아니라 Organization JSON-LD에도 적용되는 연결이다.
- 이력 복원은 위 공개 경로 외에 해당 편집 화면·이력 화면을 갱신한다. Works/Crew slug가 바뀌는 경우 **복원 전·후 두 상세 주소**를 모두 갱신한다.
- 사이트맵은 별도 직접 조회와 24시간 재검증 설정을 가지지만, Works/Crew의 일반 변경·이력 복원에서 `/sitemap.xml`도 명시적으로 갱신한다.

## 추가한 회귀 검사

새 테스트 **77개**와 기존 테스트의 추가 검증으로 다음을 확인한다.

1. 저장·삭제·휴지통 복원·강사 복제의 태그와 공개·관리 경로.
2. 강사·Crew·Works·공간 생성 후 저장 → 갱신 → 실제 새 문서로 이동하는 호출 순서. 인증·필수 입력·최종 저장 실패 시 성공 이동/갱신을 하지 않음.
3. 강사·Crew·공간의 화살표/드래그 순서 저장과 충돌 시 갱신 억제. 실패 테스트가 검증 단계에서 조기 종료한 것이 아니라 **실제 모의 커밋에 도달했는지**도 확인.
4. 여섯 이력 영역의 태그·전체 경로, 특수문자가 있는 이전/새 slug의 단일 인코딩, 저장 충돌 처리.
5. 저장·복원 커밋을 일부러 대기시켜, 완료 전에 태그·경로 갱신을 호출하지 않음을 확인.
6. 실제 Class/Crew/Works/Studio/Contact 서버 진입점·루트 레이아웃·공통 설정 조회가 올바른 태그를 사용함. 작품·Crew 상세 본문과 메타데이터의 태그도 기존 주소 회귀 검사에 연결.
7. `sanityFetch`가 공개 조회에 3600초 재검증과 전달받은 태그를 사용하고, Sanity CDN은 사용하지 않음. 초안 요청은 기존 `revalidate: 0` 및 옵션을 유지함. 읽기 실패를 가짜 데이터로 바꾸지 않음.

처음 Studio 드래그 예시에서 `group`이 빠진 모의 데이터가 실제 서버의 종류 경계 검사에 거부됐다. 모의 데이터를 `room` 구조로 수정했으며, 이 때문에 운영 코드를 완화하지 않았다.

## 최종 검증

- 전체 테스트 **1,283개 / 54개 파일** 통과.
- 타입 검사·ESLint·프로덕션 빌드 통과.
- 최종 로컬 프로덕션 서버 경로 스모크 **35/35 통과**. 공개 상세 본문·비로그인 관리 차단·noindex·보안 헤더 포함.
- 테스트는 인증·Sanity 쓰기·Next 캐시 호출을 대체한다. 실제 액션·검증·순서 처리·이력 복원 코드는 사용한다. 모의 사진은 실제 업로드하지 않는다.
- 테스트·검증 문서·README 외의 실행 소스는 이번 작업에서 수정하지 않았다. 확인용 서버는 검증 후 종료했다.

## 한계와 운영상 주의

- 이 결과는 **코드와 API 호출의 정합성** 검증이다. 실제 Vercel 캐시에 운영 문서를 저장하고 다른 브라우저에서 최신화되는 과정을 끝까지 검증했다는 뜻은 아니다. 운영 데이터 생성·수정·삭제·복원은 하지 않았다.
- 이미 열린 다른 방문자의 화면을 자동 푸시 갱신하는 기능은 아니다. 재검증되는 서버 요청과 방문자 화면의 실시간 업데이트는 구분해야 한다.
- `/manage`가 아닌 **Sanity Studio·CLI·외부 연동에서 직접 바꾼 내용은 이 액션의 갱신 호출을 거치지 않는다.** 현재 기본 공개 조회는 3600초, 사이트맵은 86400초 재검증 설정이며 실제 반영은 다음 요청과 조회 성공 여부에 따른다. 외부 변경도 즉시 반영하려면 별도 인증된 webhook과 Sanity 쪽 설정을 설계해야 한다. 이번에 webhook·시크릿·외부 서비스 설정을 추가하지 않았다.
- 초안 옵션 검사는 기존 캐시 설정을 확인한 것이며, 비공개 데이터셋 접근·초안 URL의 인증·Sanity 미리보기 전체를 새로 검증한 것은 아니다.
- 환경변수·의존성·커밋·배포는 변경하지 않았다.
