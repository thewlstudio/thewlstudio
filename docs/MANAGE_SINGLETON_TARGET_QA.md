# 단일 설정 문서의 저장 대상 점검

## 확인한 문제

- 연락처 `siteSettings`와 Studio 안내 `studioInfo`의 저장 도우미는 조회 결과의 falsy 여부만으로 최초 생성을 결정했다. SDK 이후 경계에 `null`·false·0·빈 문자열·NaN이 들어와도 문서 없음으로 추측해 생성 요청을 보낼 수 있었다.
- 기존 문서 확인도 배열·상속된 식별 정보·공백뿐인 버전을 허용했다. 다른 일반 문서에 적용한 검증과 차이가 있었다.
- 조회 예외가 발생하면 쓰기를 하지 않는 보호는 이미 있었다. 다만 Error 원문이 운영자 응답에 그대로 들어갈 수 있고, 저장 전 조회 실패라는 단계가 분명하지 않았다.
- 모의 응답에서 재현한 문제이며 실제 운영 데이터 손상이나 SDK가 정상 상황에서 이런 값을 반환한다고 확인한 것은 아니다.

## 반영 내용

- 설치된 `@sanity/client/src/data/dataMethods.ts`의 `_getDocument` 구현·반환 타입을 확인했다. 기본 `getDocument`의 문서 없음 값은 `undefined`이므로 그 값일 때만 고정 ID로 최초 생성한다. GROQ `[0]` 조회의 `null` 계약과 구분하며, 공개 페이지나 관리 폼 읽기 정책은 바꾸지 않는다.
- 배열이 아닌 객체와 자체 `_id`·`_type`·비공백 `_rev`를 요구한다. 일반 문서와 단일 설정 문서가 같은 비공개 판별 함수를 사용한다. 식별값·버전 문자열을 임의로 보정하지 않는다.
- 설정 조회 예외는 서버 오류 보고 경로에 원래 예외를 남기고, 운영자에게는 “설정 문서를 불러오지 못해 저장하지 않았어요”라는 고정 안내를 반환한다. 재시도·생성·수정으로 넘어가지 않는다.
- 정상 기존 문서는 검증한 한 번의 조회 결과와 그 버전으로만 수정한다. Studio 배열 추가 필드 검사 콜백은 여전히 바로 그 스냅샷을 대상으로 실행된다.
- 최초 생성은 기존 `create`를 유지한다. 다른 요청이 같은 ID를 먼저 만들면 409로 거부하며, `createOrReplace`나 패치로 바꿔 덮어쓰지 않는다. 수정 충돌도 새 생성이나 최신 버전 재조회로 우회하지 않는다.
- 정상 생성/패치 응답 검사·성공 후 캐시 갱신·부가 필드 보존 규칙은 유지한다. 디자인·스키마·환경변수·의존성은 바꾸지 않았다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽고 서버 함수 입력·인증·반환값 최소화 원칙을 확인했다.

## 검증

새 테스트 **46개**를 추가했다. 두 실제 서버 액션 각각에서 다음을 확인한다.

- 비정상 조회 결과 16종은 생성·패치·성공 캐시 갱신 없이 거부한다.
- 조회 예외 3종은 원문을 응답에 노출하지 않으면서 원래 예외의 서버 보고를 유지한다.
- 정상 없음/기존 문서의 생성·수정 2종에서 고정 ID·조회 1회·원본 불변성·기존 버전 조건·갱신 경로를 확인한다.
- 생성 경합/수정 충돌 2종에서 다른 요청의 원본 보존과 재조회·대체 쓰기 없음도 검사한다.
- 보완 전 26개가 실패하는 것을 재현했고, 보완 후 통과했다. 기존 일반 문서·휴지통 검증도 전체 회귀 테스트에 포함했다.
- 전체 **4,433개 / 105개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

## 범위와 한계

- CMS와 인증은 모의 구현이다. 실제 운영 문서 저장·업로드·커밋·배포 또는 인증된 브라우저 E2E는 수행하지 않았다.
- SDK가 반환한 이후의 값을 검사한다. SDK 내부에서 잘못된 전송 응답까지 `undefined`로 변환하는 경우는 이 계층에서 구분할 수 없다. HTTP 응답 검증을 새로 구현하거나 별도 조회를 추가하지 않았다.
- 서버 조회부터 패치까지의 revision 보호다. 오래 열린 두 브라우저의 모든 수정 내용을 자동 병합하거나 목록 전체를 상호 배제하는 기능은 아니다.
- 설정 내용 전체의 손상 여부를 새로 심사하거나 정상적으로 제출한 필드의 교체를 금지한 작업은 아니다. 기존 Studio 배열 원본 보호와 입력 검증 계약은 유지한다.
