# Studio JSON 입력 구조·비우기 구분 점검

## 재현한 문제

- 공간 저장·생성의 `listsJson`은 필드가 없으면 `{}`로 읽고, 배열·null·숫자·문자열인 JSON도 빈 객체로 처리했다. 이어 가격·사진·특징·안내를 빈 배열로 조립해 기존 목록을 지울 수 있었다.
- 공간과 안내 설정의 정리 함수는 잘못된 배열/행/문자열을 필터링하거나 빈 값으로 바꿨다. 누락된 안내 문구나 장비 목록도 사용자가 명시적으로 비운 것과 구분하지 않았다.
- 실제 저장 액션을 사용한 구조 테스트 241개 중 수정 전 **215개가 실패**, 기존에 거부하던 26개만 통과했다. 이는 인증 이후의 잘못된 입력에 대한 데이터 손실 위험이며, 인증 우회나 실제 운영 데이터 삭제를 재현한 것은 아니다.

## 저장 계약

관리 화면은 원래부터 전체 JSON 스냅샷을 보낸다. 새 서버 전용 `studio-content-shape.ts`는 그 구조를 확인하고, 기존 한도·중복 키·업로드·문서 쓰기보다 앞에서 실패를 반환한다. 부분 JSON을 원본과 자동 병합하거나 불완전한 입력을 빈 값으로 정리하지 않는다.

| 입력 | 처리 |
| --- | --- |
| JSON 필드 누락·빈 값·잘못된 문법·File | 오류, 저장하지 않음 |
| 최상위 배열·null·숫자·문자열 | 오류, 저장하지 않음 |
| 필수 필드 누락·잘못된 목록/행/문자열 자료형 | 해당 입력 묶음 오류, 저장하지 않음 |
| 완전한 스냅샷의 명시적인 `[]`·빈 문자열 | 기존 비우기/필수 값 정책에 따라 저장 |

### 공간 `listsJson`

- `prices`, `images`, `features`, `notes` 네 배열이 모두 있어야 한다.
- 가격 행은 객체이며 라벨·금액·단위가 문자열이어야 한다. 모두 빈 문자열인 행은 기존처럼 정리할 수 있지만, `{}`나 `null`을 빈 가격 행으로 보지는 않는다.
- 사진 행은 비어 있지 않은 문자열 `_key`가 있어야 한다. 사진을 찾거나 파일 입력과 연결할 수 없는 행을 조용히 건너뛰지 않는다. 에셋은 기존처럼 서버 원본/파일에서만 가져온다.
- 특징·안내는 문자열 배열이어야 한다. 빈 문자열·공백만 있는 문자열을 정리하는 기존 동작은 유지한다.

### 안내 `dataJson`

- 서비스·장비·멤버십·편의시설 배열과 폼이 관리하는 일반 문구 10개가 모두 있어야 한다. 비워두고 싶은 문구도 필드를 생략하지 않고 빈 문자열로 보낸다.
- 서비스 행은 제목·금액·단위 문자열과 문자열 배열 `points`, 장비 행은 제목 문자열과 문자열 배열 `items`, 멤버십 행은 숫자·이름·영문 이름·금액 문자열을 갖는다.
- 가격/안내 행의 `_key`는 이전처럼 미지정 시 서버 발급을 지원하되, 명시한다면 문자열이어야 한다. 중복 키 거부는 기존 공통 정책이 담당한다.
- 서비스·장비 제목과 멤버십 이름·금액이 비어 있는 경우는 기존 의미 검증에서 계속 거부한다. 해당 카드 배열 자체를 명시적으로 비우는 것은 허용한다.

## 동작과 호환성

- 기존 두 폼은 이미 필요한 필드를 모두 보내므로 정상 입력 방식은 바뀌지 않는다. 원본 CMS에 없는 선택 필드는 관리 페이지의 기존 정규화 단계에서 빈 문자열/배열로 채워진다.
- 누락된 필드를 조용히 보정하는 운영 코드는 추가하지 않았다. 직접 액션을 호출하는 별도 스크립트가 있다면 완전한 폼 형식을 보내야 한다. 이 경로는 부분 수정용 API가 아니다.
- 잘못된 입력은 문서 조회/패치·생성·사진 업로드·캐시 갱신 전에 반환한다. 인증과 이미지 전체 용량 검사는 기존 순서를 유지하며, 쓰기 클라이언트 구성 실패가 입력 검사보다 먼저 발생할 수 있다는 제한도 유지한다.
- 오류 요약은 실제 입력/묶음 ID를 가리킨다. 원문 JSON·기본 정보·dirty 상태를 유지하고 자동 새로고침하지 않는다. 원문 값이나 예외 객체를 사용자 오류 문구에 넣지 않는다.
- 한도·중복 키·revision 조건·정상 저장의 캐시 갱신·명시적인 비우기는 그대로 유지했다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. CMS 스키마·전송 본문 한도·인증 설정은 변경하지 않았다.

## 검증

새 테스트 **257개**를 추가했다.

- 잘못된 구조의 실제 액션 **241개**: 공간 수정/생성 각 61개, 안내 저장 119개. JSON 누락·잘못된 문법/최상위 형태, 필수 배열·문구 누락, null/객체/숫자/배열을 문자열로 오인하는 경우, 중첩 목록·사진 키 누락 등을 검사했다. 거부 시 문서·revision·업로드·생성/이동·캐시를 변경하지 않는다.
- 정상 비우기·인증·보조 규칙 **12개**: 공간 수정/생성의 명시적인 빈 배열, 안내 전체/일부 문구 비우기, 세 액션의 File 거부와 인증 우선 처리, 입력 불변성과 상속 필드 거부, 배열 빈 슬롯 처리.
- 실제 폼 DOM **4개**: 두 폼이 실제로 만드는 JSON의 구조 검사 통과, 구조 오류 응답 후 입력과 dirty 보존 및 오류 요약 포커스 이동.

기존 저장 테스트의 축약 fixture는 `src/test/studio-payloads.ts`를 사용해 실제 폼처럼 완전한 스냅샷으로 만들었다. 이 도우미는 테스트 전용이다. 새 오류 테스트는 이 정상 fixture에서 필드를 삭제하거나 잘못된 자료형을 주입하므로 잘못된 입력이 도우미에 의해 정상화되어 숨겨지지 않는다.

전체 **1,982개 / 62개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크 **35/35 통과**.

초안·휴지통을 제외한 공개 공간 **5건**과 고정 안내 **1건**을 읽기 전용으로 조회했다. 원본 문서 그대로가 아니라 실제 관리 페이지와 같은 선택 필드 정규화와 안내 `mergeInfo`를 거친 제출 형태를 구성해 새 구조 검사를 통과함을 확인했다. 거부 **0건**, 문서/에셋 쓰기 **0회**. 원문 값이나 인증 정보는 출력하지 않았다.

## 범위와 남은 점검

- 운영 저장·실제 사진 업로드·인증된 운영 브라우저 E2E·배포는 하지 않았다. 액션 테스트는 모의 Sanity와 검증용 파일을 사용한다. 네트워크에서 잘린 multipart 요청의 실제 전송 E2E를 검증한 것은 아니다.
- 이 구조 계약은 Studio 공간·안내의 세 액션에만 적용했다. Works·Crew 본문, 강사 문단 등 다른 입력의 자료형 계약까지 모두 완료했다는 의미는 아니다.
- 필드의 의미·알 수 없는 확장 메타데이터·CMS에 이미 저장된 잘못된 자료형까지 자동 복구하는 작업은 아니다. 이후 [안내 키 보존 점검](STUDIO_INFO_KEYS_QA.md)에서 안내 편집기의 조회·폼·저장 키 왕복도 보완했다.
- 정상 디자인·운영 문서·에셋·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
