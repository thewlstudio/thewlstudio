# Works·Crew 본문 저장 한도 점검

## 확인한 문제

- 블록·섹션 편집기는 긴 글과 여러 항목을 입력할 수 있었지만, 서버의 `slice`가 글자 수·중첩 목록 초과분을 자른 뒤 성공을 반환했다. 예를 들어 301자인 트랙 제목은 300자로, 101개인 경력은 100개로 저장될 수 있었다.
- 최상위 블록 30개·섹션 20개에는 이미 오류 처리가 있었지만, 문단·트랙·크레딧·연도 묶음 등 내부 배열과 텍스트에는 같은 기준이 적용되지 않았다.
- 종류 판별의 `in`은 `constructor`, `toString` 같은 상속 속성도 인정했다. 실제 모델에 없는 종류가 보존 경로 대신 편집 경로로 들어가 내용이 누락되거나 다른 모양으로 정리될 수 있었다. 프로토타입 오염이나 인증 우회를 재현한 것은 아니다.

## 반영 내용

기존 한도를 늘리거나 줄이지 않고, 초과하면 내용을 잘라 저장하는 대신 오류를 반환한다.

| 대상 | 유지한 한도 |
| --- | --- |
| Works 최상위 블록 | 30개 |
| Works 문단·트랙·크레딧 묶음·묶음 내 항목 | 각 배열 100개 |
| Works 문단·트랙 설명·크레딧 내용 | 각 10,000자 |
| Works 제목·서명·캡션·크레딧 짧은 필드·오디오 제목/아티스트 | 각 300자 |
| Works 유튜브·크레딧 링크 주소 | 각 1,000자 |
| Crew 최상위 섹션 | 20개 |
| Crew 연도 묶음·트랙·경력·수상·활동·학력·자격증 | 각 배열 100개 |
| Crew 소개 글 | 5,000자 |
| Crew 나머지 한 줄 필드 | 각 300자 |

- 글자 수는 기존 JavaScript 문자열 길이(UTF-16 코드 단위) 기준이다. 이모지의 시각적 개수와 다를 수 있다.
- 기존 텍스트 정리 순서를 유지한다. Works 본문은 CRLF를 LF로 통일한 뒤 검사하고, Crew 소개 글은 줄바꿈 정리·앞뒤 공백 제거 뒤 검사한다. Crew 한 줄 필드는 기존처럼 앞뒤 공백만 제거한다.
- Works는 모든 편집 블록의 길이·개수를 먼저 검사하므로, 앞쪽 사진 블록 뒤에 한도 초과 내용이 있어도 사진 업로드 콜백을 실행하지 않는다.
- Crew는 섹션 검사 뒤 링크 아이콘·대표 사진을 업로드하도록 순서를 바꿨다. 본문 한도 오류로 불필요한 아이콘 에셋이 생기는 것을 방지한다.
- 오류에는 블록/섹션 위치와 항목 이름·한도를 표시한다. 기존 액션의 `blocks`/`sections` 필드 오류 경로를 사용하므로 요약에서 해당 편집기로 이동할 수 있다. 실패 후 입력·dirty 상태는 유지한다.
- `Object.hasOwn`으로 실제 등록된 종류만 판별한다. 알 수 없는 종류는 기존 보존 경로를 따른다. 자유서식·예전 섹션 원본에는 편집 가능한 필드의 새 검사를 소급 적용하지 않는다.
- 빈 항목 정리, 기존 파일 보존, 종류별 편집 범위, revision 조건과 캐시 갱신 정책은 유지한다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 액션 인증·서버 전용 경계를 변경하지 않았다.

## 검증

새 회귀 테스트 **60개**를 추가했다.

- 길이·개수 경계 **46개**: Works 19종 경계와 업로드 전 전체 검사·보존 블록·CRLF, Crew 20종 경계와 예전 형식·정규화, 공통 도우미의 비문자열/비배열 처리. 정상 경계값의 내용 보존과 초과값의 오류·입력 불변성을 확인했다.
- 종류 판별 **8개**: 두 모델에서 상속 속성 4개씩을 미등록 종류로 처리하고 원본을 보존한다.
- 실제 저장 액션 **4개**: Works 긴 문단/101개 트랙, Crew 긴 소개/101개 경력. 함께 보낸 사진·링크 아이콘도 업로드하지 않고 문서·revision·캐시를 바꾸지 않는다. Sanity는 모의 저장소를 사용했다.
- 실제 폼 DOM **2개**: 저장 실패 후 본문 JSON·기본 정보·dirty 유지, 오류 요약에서 해당 편집기로 포커스 이동, 자동 새로고침 없음.

전체 **1,596개 / 59개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 서버 경로 스모크도 **35/35 통과**했다.

현재 CMS의 초안·휴지통을 제외한 **Works 8건·Crew 3건**을 읽기 전용으로 조회했다. 실제 모델 변환과 정리 함수를 적용했을 때 오류 **0건**, 새 파일 업로드 **0회**였다. 문서 원문이나 인증 정보를 로그에 출력하지 않았다. 이는 한도와 기존 정리 규칙을 통과한다는 확인이며 전체 필드의 바이트 단위 무손실을 증명하는 검사는 아니다.

## 범위와 한계

- 운영 CMS 쓰기·실제 브라우저 저장 E2E·배포는 하지 않았다. 테스트 파일은 실제 사진이 아닌 모의 바이트도 사용한다.
- 기존에 한도를 넘는 알려진 종류의 콘텐츠가 있다면 다른 기본 정보만 바꿔도 본문 전체를 함께 제출하는 저장은 거부될 수 있다. 이때 본문을 임의로 삭제하지 말고, 필요하면 `/admin` 또는 한도 정책 검토를 거쳐 처리한다. 현재 공개 조회 대상 11건에서는 이 상황이 없었다.
- 공백만 있는 항목 제거·빈 블록 정리 같은 기존 동작은 유지했다. 이 점검 당시 범위 밖이었던 잘못된 자료형 처리는 이후 [본문 입력 구조 점검](BODY_INPUT_SHAPE_QA.md)에서 보완했다. 알 수 없는 필드까지 일반적으로 무손실 편집하는 기능은 아니다.
- 길이·개수 오류는 업로드 전에 차단하지만, 이후 다른 검증이나 네트워크 오류까지 포함한 전체 요청의 부작용 없음·트랜잭션성을 보장하는 변경은 아니다.
- 정상 콘텐츠 디자인·운영 데이터·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
