# 강사·Crew·Works·공간 상세 원본 읽기 점검

## 재현한 문제

- 강사 조회 결과를 타입 선언만 믿고 폼에 넘겼다. `about`/`process`가 문자열 목록이 아니면 폼의 `join()`에서 오류가 나거나 객체를 문자열로 바꿀 수 있었고, 잘못된 `portfolioText`는 `replace()` 오류를 일으킬 수 있었다.
- Crew·Works 편집 상태 변환은 잘못된 문자열·배열을 빈 값으로 정리한다. 원본의 잘못된 자료형을 확인하지 않으면 기존 내용이 비어 보인 채 저장될 수 있었다.
- 공간 사진, Crew 링크, Works 미디어·미지원 보존 블록에 원본 키가 없으면 임시 키로 바뀐다. 서버가 같은 원본 행을 찾지 못해 사진·아이콘 메타데이터 또는 보존 내용을 연결하지 못할 수 있었다.
- GROQ의 배열 투영은 원본의 잘못된 컨테이너나 행을 숨길 수 있다. 투영한 결과만 검사하는 것으로는 충분하지 않았다.
- 실제 상세 페이지의 회귀 테스트 28개 중 수정 전 **16개가 실패**했다. 정상 예전 문서, 명시적 null의 404, 조회 예외 전달 12개는 이미 통과했다. 운영 데이터 손실이 발생했다고 확인한 것은 아니다.

## 반영 내용

- 네 상세 편집 화면에서 **원본 검사 → DTO 기본값 변환 → 폼 표시** 순서를 적용했다. 조회 응답을 `unknown`으로 받아 ID·문서 종류·revision과 사용하는 필드의 자료형을 먼저 확인한다.
- 명시적 `null`만 기존 404로 처리한다. 예상 밖 응답은 읽기 실패 안내를 보여주며, 실제 조회 예외는 기존 오류 경계로 전달한다. 다른 종류의 문서는 기존 종류 필터에 따라 404가 될 수 있다.
- 잘못된 원본에는 편집 폼과 해당 문서의 삭제·복사·복원 버튼을 렌더링하지 않는다. `role="alert"` 안내에 고정된 항목 이름과 기존 `/admin` 원본 확인 경로를 제공한다. 원본 값·오류 객체는 안내에 출력하지 않는다.
- 없는/null 선택 필드와 정상적인 빈 문자열·빈 배열은 계속 허용한다. 강사 분류·사진 위치 등에 임의의 열거형을 새로 강제하지 않았다.
- Crew·Works의 알려진 본문 종류는 중첩 자료형과 중복 키를 검사한다. 지원되는 예전 문자열 경력은 유지한다. 학력·자격증의 객체 행처럼 저장 시 제목 외 정보가 사라지는 형태는 조용히 정리하지 않는다.
- 원본 참조가 필요한 공간 사진·Crew 링크·Works 미디어/미지원 블록은 비어 있지 않은 원본 키를 요구한다. 원본 키의 `new-`·`legacy-` 접두사는 해석하지 않는다. 같은 배열의 중복 키도 차단한다.
- 알 수 없는 보존 본문은 내부 내용을 임의로 해석하지 않는다. 종류·원본 키로 식별해 기존 서버 보존 경로를 유지한다.
- Crew 링크, Works 본문, 공간 가격·사진에 원본 배열 별칭을 추가했다. 투영 전 자료형도 검사하고 행 수·순서별 키(Works는 종류 포함)가 일치하는지 확인한다. Crew·Works의 `slug.current` 투영 전 주소 자료형도 확인한다. 이 별칭 전체를 폼 데이터에 추가하지 않는다.
- 미리보기 주소를 못 읽었다는 이유만으로 사진·오디오를 차단하거나 제거하지 않는다. 원본 키가 있으면 기존 nullable URL과 원본 보존 정책을 유지한다.
- 기존 설정 읽기 안내를 재사용하되 상세 화면에는 ‘설정’ 대신 ‘내용’으로 표시한다. 연락처·Studio 안내의 기존 문구와 동작은 유지한다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 저장 액션·권한·revision 조건·캐시 갱신 정책은 변경하지 않았다.

## 검증

새 테스트 **188개**를 추가했다.

- 서버 전용 판별 함수 **160개**: 네 문서의 메타데이터·스칼라·공개/휴지통 상태·중첩 본문·원본 키·중복 키·투영 누락·원본 불변성·안내의 원문 미포함·정상 예전 데이터 호환.
- 실제 상세 페이지 SSR **28개**: 정상 폼 유지, 잘못된 원본과 식별 정보의 폼/변경 버튼 미출력, 조회 예외 전달, 명시적 null의 404. 저장소와 폼·내비게이션 일부는 모의 구현이다.
- 기존 조회 보존 fixture에 실제 응답의 문서 종류와 원본 배열 별칭을 추가했다. 저장된 키 없는 Crew 링크는 새 키로 편집하기보다 원본 확인 안내로 바뀌었으므로 해당 1개 기대값을 변경했다. 정상 사진·아이콘 메타데이터의 반복 저장·재조회 테스트는 유지했다.

전체 **2,496개 / 72개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크도 **35/35 통과**했다.

공개 API를 읽기 전용으로 조회해 실제 판별 함수를 적용했다. 초안·휴지통을 제외한 **강사 7건, Crew 3건, Works 8건, 공간 5건(총 23건)** 모두 차단 항목 **0개**였다. 문서 식별 값·원문·인증 정보는 출력하지 않았고 CMS 쓰기는 하지 않았다.

## 범위와 한계

- 상세 화면의 **UI 읽기 보호**다. 저장 API에 새 권한 정책을 추가하거나 직접 호출을 금지한 것은 아니다. 다른 관리 도구에서도 손상된 문서가 절대 변경되지 않는다는 보장은 아니다.
- 필드의 업무상 정확성·모든 URL/날짜 의미·글자 수 한도·스키마 확장 정보까지 검사하는 범용 복구 도구가 아니다. 누락 선택 값은 기존 전체 폼 저장 계약대로 빈 값/기본값으로 저장될 수 있다.
- 알려진 본문의 현재 편집 대상 필드만 검사한다. 알 수 없는 확장 필드 전체에 무손실 왕복을 보장하거나 과거 손실을 복구하지 않는다.
- 키가 없는 원본을 자동 수정하거나 아이콘·사진을 추측해 연결하지 않는다. 차단 시 새로고침 후에도 같으면 기존 `/admin` 또는 개발자를 통해 원본을 확인해야 한다.
- 목록 화면의 비정상 원본까지 이번 단계에서 일반화한 것은 아니다. 이 문서의 범위는 네 상세 편집 화면이다.
- 후속 [목록 원본 읽기 점검](MANAGE_LIST_READ_QA.md)에서 네 목록·휴지통의 식별·표시·상태·개수 검사와 썸네일 오류 격리를 추가했다. 목록에서 전체 상세 본문을 검사하는 것은 아니다.
- 운영 CMS 저장·인증된 운영 브라우저 E2E·새 안내의 시각/스크린리더 실기 검증·배포는 하지 않았다. 정상 공개 디자인·운영 데이터·스키마·환경변수·의존성·커밋은 변경하지 않았다.
