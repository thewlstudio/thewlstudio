# Works·Crew 본문 입력 구조·원본 참조 점검

## 재현한 문제

- 본문 정리 함수가 객체가 아닌 블록·섹션을 건너뛰고, 없는 배열이나 문자열이 아닌 값을 빈 값으로 바꿨다. 문단·트랙·경력 정보 일부가 잘못되거나 누락되어도 본문을 비우거나 일부를 버린 뒤 성공할 수 있었다.
- 새로 만든 오디오 참조나 원본에 없는 알 수 없는 종류를 조용히 버렸다. Crew 예전 형식은 종류가 달라도 같은 키만 맞으면 원본을 가져왔다.
- Works 보존 블록 누락 검사가 모든 블록 처리 후에 있었다. 따라서 앞쪽 새 사진을 업로드한 뒤 마지막에 보존 오류를 반환할 수 있었다.
- 실제 편집기가 보내는 자료형 계약 테스트 **169개**를 먼저 작성했으며, 수정 전 **159개가 실패**, 이미 거부하던 10개만 통과했다. 이는 인증된 입력의 무결성 문제이며, 인증 우회나 운영 데이터 삭제를 수행한 것이 아니다.

## 반영한 구조 계약

서버 전용 `body-content-shape.ts`로 제출된 **전체 본문 구조와 원본 참조를 먼저 검사**한다. 실패하면 기존 `blocks`/`sections` 필드 오류를 반환하고 이미지·아이콘 업로드나 문서 쓰기로 진행하지 않는다.

### Works

- 각 블록은 객체이며 비어 있지 않은 문자열 `_type`이 있어야 한다. 편집 가능한 본문은 화면이 보내는 필수 필드를 모두 갖는다.
- 설명·인사말은 문자열 문단 배열, 인사말 서명은 문자열이다. 트랙은 제목·설명 문자열을 가진 객체 배열이다.
- 크레딧 묶음은 제목 문자열과 항목 배열, 각 항목은 역할·내용·링크 이름·링크 주소 문자열을 갖는다.
- 사진은 비어 있지 않은 문자열 키와 캡션 문자열, 유튜브는 주소 문자열을 갖는다. 미디어 주소 의미 검사는 기존 함수를 그대로 사용한다.
- 오디오는 제목·아티스트 문자열과 기존 문서에 있는 같은 키·종류의 참조가 필요하다. 파일 업로드는 기존처럼 `/admin`에서 한다. 없는 오디오 참조를 조용히 버리지 않는다.
- 자유서식과 알 수 없는 보존 종류는 같은 키·종류의 원본이 있을 때만 허용하고, 클라이언트가 보낸 내용은 사용하지 않는다. 보존 블록이 빠진 요청도 업로드 전에 거부한다.

### Crew

- 소개는 문자열, 음반은 연도 문자열과 트랙 배열, 음반 트랙은 제목·설명 문자열을 갖는다.
- 경력은 제목·날짜·설명 문자열의 객체 배열이다. 수상·활동은 각각 제목·날짜 문자열의 객체 배열이어야 한다.
- 학력·자격증은 문자열 배열이다. null·숫자·배열·객체를 빈 문구로 정리하지 않는다.
- 예전 형식은 같은 키 **및 같은 종류**의 서버 원본만 가져온다. 클라이언트가 보낸 내용으로 바꾸지 않는다. 원래부터 지원하던 명시적 삭제와 수상/활동의 새 형식 이전은 유지한다.

텍스트형 행 키는 기존처럼 미지정 시 서버 발급을 허용하되, 명시하면 문자열이어야 한다. 사진·오디오·보존 참조에는 실제 연결용 비어 있지 않은 키가 필요하다. 중복 키·길이·개수·필수 의미 검증은 기존 정책을 유지한다. 원본 배열에 객체 아닌 행이 있으면 무시해서 저장하지 않고 오류를 반환한다.

## 비우기와 JSON 필드 자체의 생략

| 요청 | 처리 |
| --- | --- |
| `blocksJson`/`sectionsJson` 자체를 보내지 않음 | 기존 기본 정보 저장 계약 유지: 본문을 패치하지 않음 |
| JSON 필드를 보냈으나 빈 문자열·File·잘못된 문법/최상위 형태 | 오류, 저장하지 않음 |
| 배열 안의 잘못된 행·누락된 필수 필드·잘못된 중첩 자료형 | 오류, 저장하지 않음 |
| 명시적인 빈 배열·빈 문자열 | 기존 빈 블록 정리/삭제 정책 유지 |

Studio의 전체 스냅샷 계약과 달리 Works·Crew의 본문 JSON 자체는 기존처럼 생략할 수 있다. 생략이 본문 삭제를 뜻하지 않기 때문이다. 단, Works 보존 블록이 있는 상태에서 `[]`를 보내 그 블록까지 지우는 동작은 계속 허용하지 않는다.

선택하지 않은 새 이미지, 빈 문단·트랙·경력 정리는 유지했다. 오류 뒤 실제 폼의 원문 JSON·기본 정보·dirty 상태가 남고 오류 요약에서 해당 편집기로 이동한다. 자동 새로고침은 하지 않는다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 인증·문서 종류·revision 조건·쓰기 토큰·캐시 갱신 정책은 변경하지 않았다.

## 검증

새 테스트 **214개**를 추가했다.

- 자료형 계약 **169개**: 알려진 블록/섹션의 배열·문구·중첩 필드 누락과 잘못된 값, 최상위 잘못된 행, 문단·학력 항목 형태.
- 중첩 행·참조·명시적 정리 **17개**: 트랙/크레딧/연도/경력/수상/활동의 잘못된 행, 미디어·보존 키, 원본과 다른 종류, 없는 알 수 없는 참조, 보존 누락의 업로드 전 차단, 빈 블록·미선택 사진, Crew 예전 형식 이전.
- 실제 저장 액션 **26개**: JSON 문법/형태·File 거부, 본문 미전송 시 보존, 명시적인 빈 배열, 인증 우선, 뒤쪽 본문 오류 시 앞쪽 사진/아이콘 미업로드, 사진 crop/hotspot·오디오 파일·자유서식·예전 섹션의 서버 원본 보존. Sanity는 모의 저장소를 사용했다.
- 실제 폼 DOM **2개**: 구조 오류 응답 뒤 원문·기본 정보·dirty 유지, 오류 요약에서 편집기로 포커스 이동, 자동 새로고침 없음.

기존 한도/키/이미지 저장 테스트의 축약 fixture는 `src/test/body-payloads.ts`를 사용해 실제 `toState`→`toPayload` 형식으로 구성했다. 이 테스트 전용 도우미를 새 잘못된 입력 주입 테스트에 적용해 오류를 감추지 않았다. 기존에 없던 오디오를 조용히 생략한다는 옛 기대값은 명시적 오류로 바꿨다.

전체 **2,220개 / 66개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크 **35/35 통과**.

초안·휴지통을 제외한 공개 Works **8건**·Crew **3건**을 읽기 전용으로 조회했다. 실제 편집 모델 변환과 실제 본문 저장 정리를 적용했을 때 거부된 항목은 **0건**이었다. 업로드 콜백은 항상 null을 반환하는 함수로 대체했으며, 문서·에셋 쓰기를 하지 않았다. 원문 값·인증 정보도 출력하지 않았다.

## 범위와 한계

- 운영 저장·실제 미디어 업로드·인증된 운영 브라우저 E2E·배포는 하지 않았다. 모의 저장소 검증은 실제 multipart 전송/네트워크/캐시 E2E 전체를 대신하지 않는다.
- 이번 업로드 전 차단은 구조·키 참조·보존 누락과 기존 한도 검사에 관한 것이다. 이후 URL 의미 검증·네트워크/API 오류 등 모든 실패 경로의 부작용 없음이나 완전한 트랜잭션성을 보장하지 않는다.
- 과거에 손실된 내용·키를 자동 복구하거나, CMS 원본의 모든 잘못된 자료형·알 수 없는 확장 메타데이터를 고치는 작업은 아니다. 이후 [조회·저장 원본 보존 점검](MANAGE_READ_PRESERVATION_QA.md)에서 Studio 사진 행 필터와 Crew 링크 원본 키 전달도 보완했다. 모든 원본 자료형의 자동 복구를 뜻하지는 않는다.
- 정상 디자인·운영 데이터·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
