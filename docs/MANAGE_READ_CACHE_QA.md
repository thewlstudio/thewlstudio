# 관리자 읽기 캐시·최신 데이터 조회 정책 점검

## 결론

- 현재 구성에서 별도의 Sanity CDN 캐시나 공개 ISR 캐시를 관리자 데이터 조회에 잘못 재사용하는 결함은 추가로 확인하지 않았다. 정상 구성을 불필요하게 다시 작성하지 않았다.
- 관리자 전체의 동적 렌더링 정책을 중앙 레이아웃에 명시하고, 조회 경로와 실제 HTTP 캐시 헤더에 대한 회귀 검사를 보강했다. 이번 결과를 운영에서 오래된 데이터가 실제 제공됐다는 증거로 해석하면 안 된다.

## 확인한 정책

- 공개 `client`와 서버 변경/이력용 `getWriteClient`는 모두 `useCdn: false`다. Sanity API CDN을 거치지 않는다.
- 공개 홈페이지는 별도 `sanityFetch`를 통해 기본 3,600초 재검증·영역별 태그를 사용한다. 미리보기는 재검증 0을 사용한다. 이 정책은 바꾸지 않았다.
- 관리자 CMS 조회 페이지 12곳은 인증 확인 후 읽기를 시작한다. 목록/휴지통·수정 상세·단일 설정·허브·변경 이력을 포함한다. 공개 `sanityFetch`나 영구 데이터 캐시 래퍼를 관리자 코드에서 호출하지 않는다.
- 기존 목록·상세·설정·이력에는 개별 `force-dynamic` 선언이 있었다. 허브·로그인·도움말 등은 인증 쿠키/요청 정보에 동적 처리를 의존하고 있었다.
- 변경·복원 액션의 현재 버전 조회는 CDN이 꺼진 쓰기 클라이언트를 사용한다. 일반 서버 조회에 영구 cache override를 붙이지 않는다. 기존 인증·revision 조건·저장 응답 확인 규칙은 그대로 유지한다.

## 보강 내용

- `/manage/layout.tsx`에 `dynamic = "force-dynamic"`을 명시했다. 개별 페이지의 선언 누락이나 로그인 설정에 따른 쿠키 조회 분기와 무관하게 관리자 HTML의 정책을 유지한다. 공개 루트 레이아웃이나 공개 캐시 설정을 전역 비캐시로 바꾸지 않았다.
- 스모크 검사에서 관리자 HTML/로그인 이동 응답의 `Cache-Control`을 수집해 `private`·`no-store`와 `public` 충돌 여부를 확인한다. 로그인 포함 13개 응답을 하나의 집계 검사로 확인한다. 헤더가 없거나 잘못돼도 정상 통과하지 않는다.
- `robots.nocache` 메타데이터와 HTTP 캐시 지시자는 별개다. 이번 검사는 실제 HTTP 응답 헤더를 확인한다.
- 임의 timestamp·추가 AbortSignal·강제 중복 조회·새 전역 클라이언트는 넣지 않았다. 같은 렌더링 중의 요청 메모이제이션은 요청 간 영구 캐시와 다르므로 그대로 둔다.

## 기준 문서와 SDK

- 설치된 Next.js의 `04-functions/fetch.md`와 `02-guides/caching-without-cache-components.md`를 읽었다. 현재 프로젝트는 Cache Components를 사용하지 않으며, `force-dynamic`은 해당 경로의 fetch 비캐시 정책을 강제한다. 추후 Cache Components를 활성화하면 이 구성을 다시 검토해야 한다.
- 설치된 Sanity SDK의 `data/dataMethods.ts`와 `http/requestOptions.ts`에서 Next의 cache/next 옵션 전달과 클라이언트 fetch 설정 병합을 확인했다.
- 개발 중 HMR 캐시는 `no-store` 조회에도 적용될 수 있다. HMR에서 예전 값이 보였다고 운영 캐시 결함으로 단정하거나 공개 ISR/HMR을 전역 해제하지 않는다. 새 탐색·전체 새로고침·프로덕션 모드와 구분해서 확인해야 한다.

## 검증

새 테스트 **23개**를 추가했다.

- 관리자 소스 정책 15개: 중앙 동적 설정·CMS 읽기 페이지 목록·12곳의 인증 선행·공개 ISR/영구 캐시 사용 방지.
- 서버 클라이언트 2개: 미설정 시 클라이언트 생성 차단, 설정 시 CDN 비활성·별도 fetch override 없음. 토큰은 테스트용 값만 사용한다.
- 스모크 검사 자체 6개: 캐시 지시자 누락/충돌 5종의 실패 검출, 대소문자가 다른 안전한 지시자 허용.
- 기존 공개 CDN 비활성·공개 1시간/미리보기 0 캐시·태그·공개 데이터 소비 지점 테스트도 통과했다.
- 전체 **4,671개 / 110개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 빌드 manifest의 사전 렌더링 관리자 경로는 **0개**다.
- 실제 로컬 프로덕션 HTTP 점검은 **38/38 통과**했다. 기존 37개 검사에 관리자 13개 응답의 캐시 헤더 집계 검사 1개가 추가됐다. 임시 서버는 종료했다.

## 범위와 한계

- 소스 검사와 SDK 생성 검사는 구조/설정 회귀를 잡는 테스트이며 모든 별칭·간접 호출의 동작을 증명하는 정적 분석기는 아니다.
- 실제 HTTP 확인은 로그인 화면과 비로그인 관리자 접근 차단 응답이다. 인증된 관리 화면의 실제 CMS 조회·운영 저장 직후 readback 종단 테스트는 수행하지 않았다.
- Next/Sanity 캐시 우회를 확인한 것이지 모든 조회가 같은 DB 스냅샷이라는 뜻은 아니다. 여러 요청/브라우저 사이의 최신 revision 도착을 증명하거나 데이터 소스의 모든 지연을 없애는 프로토콜은 추가하지 않았다.
- 이번 헤더 집계는 HTML 페이지 경로 대상이다. 미리보기 등 Route Handler의 응답 헤더/리다이렉트 정책을 모두 포함한 검사는 아니다.
- 운영 데이터·업로드·커밋·배포·디자인·스키마·환경변수·의존성은 변경하지 않았다.
