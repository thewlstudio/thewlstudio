# 관리자 조회·폼·저장 간 원본 보존 점검

## 재현한 문제

### Studio 사진

공간 수정 페이지가 `asset->url`을 읽지 못한 사진 행을 `.filter(im => im.url)`로 제외했다. 저장 액션은 폼이 제출한 사진 목록으로 배열을 교체하므로, 이름 등 다른 정보만 저장해도 빠진 원본 사진 참조가 삭제될 수 있었다. 미리보기 주소가 없다는 것과 사진 행이 없다는 것을 혼동한 경로다.

### Crew 링크

조회 페이지가 원본 `_key`를 화면 `key`에 그대로 넣고, 폼은 `new-`·`legacy-` 접두사가 있는 키를 새 행/키 없는 예전 행으로 판단해 숨은 `linkKey_i`를 보내지 않았다. 실제 원본 키가 이 접두사를 가지면 저장 시 키가 바뀌고, 같은 원본 행에 연결된 아이콘 crop/hotspot을 찾지 못할 수 있었다. 서버 공통 키 함수도 `new-` 접두사를 임시 키로 판단했다.

기본 조회·폼 회귀 테스트 11개 중 수정 전 **9개가 실패**했다. 이 재현은 모의 원본을 사용했으며 실제 운영 데이터에서 이미 손실이 발생했다는 증거는 아니다.

## 반영 내용

### 사진 행은 URL 유무로 삭제하지 않는다

- 공간 수정 조회의 사진 URL 필터를 제거했다. 원본 키와 순서는 유지하고, 없는 미리보기 주소는 `null`로 표현한다.
- 폼의 저장 사진 타입도 nullable URL을 받도록 맞췄다. URL 없는 원본 행도 저장 JSON에 키를 남겨 서버가 현재 문서에서 사진·crop·hotspot·추가 메타데이터를 유지한다.
- 이 경우에는 미리보기 주소를 읽지 못했지만 기존 사진 정보를 유지하며 필요하면 교체할 수 있다는 안내를 표시한다. 정상 미리보기가 있는 사진의 UI는 바꾸지 않았다.
- URL 없는 원본 사진도 기존 순서 변경·명시적 삭제 기능으로 처리할 수 있다. 자동으로 숨기거나 지우지 않는다.

### Crew 화면 키와 원본 키를 구분한다

- 조회한 원본 키는 `sourceKey`로 전달한다. 화면 내부 `key`는 `stored-0` 같은 별도 값으로 만들어 원본 키의 문자·접두사를 UI 식별 규칙으로 해석하지 않는다.
- 키가 없는 예전 행은 `legacy-i` 화면 키와 미지정 `sourceKey`로 구분한다. 새 행에는 기존처럼 임시 화면 키만 있으며 원본 키를 위장해 보내지 않는다.
- 후속 [상세 원본 읽기 점검](MANAGE_DETAIL_READ_QA.md)에서는 저장된 링크의 키가 없으면 폼 진입 전에 원본 확인을 안내하도록 보강했다. 위 `legacy-i` 구분은 이 단계 당시 구현 기록이며 정상 신규 행에는 원본 키가 없는 기존 정책을 유지한다.
- 폼은 `sourceKey`가 있으면 접두사와 관계없이 실제 원본 키를 `linkKey_i`로 보낸다. 이전 props 형식의 일반 원본 키에 대한 기존 동작도 유지한다.
- 서버는 현재 문서의 같은 원본 행을 찾았으면 키를 그대로 유지한다. 기존 원본의 `new-` 접두사를 새 항목처럼 재발급하지 않는다. 새 행은 기존 공통 발급 규칙을 사용한다.
- 같은 행·같은 아이콘 참조의 서버 원본 메타데이터 보존, 다른 아이콘 선택/새 업로드의 기존 교체 규칙, 중복 키·링크 수·URL 검사는 유지한다.

Works 사진·오디오는 URL을 못 읽어도 본문 블록 자체를 조회 데이터에서 제거하지 않는 것을 확인했으며 이 부분의 운영 코드는 바꾸지 않았다. 단일 대표 사진처럼 업로드가 없으면 패치하지 않는 기존 경로도 이번 수정 대상이 아니다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 인증·문서 종류·revision 조건·캐시 갱신·쓰기 토큰·전송 용량 정책은 변경하지 않았다.

## 검증

새 테스트 **17개**를 추가했다.

- 실제 조회 페이지 **8개**: Studio URL null/미지정/빈 문자열 3개, Crew 접두사·일반 원본 키 3개, 키 없는 예전 링크 1개, Works 사진/오디오 URL null의 본문 보존 1개.
- 실제 폼 DOM **3개**: URL 없는 사진의 저장 JSON·안내, `new-`/`legacy-` 원본 키의 hidden 입력 보존.
- 실제 조회 페이지→실제 폼→실제 액션→모의 저장소→새 revision 재조회 **6개**: Studio의 다른 필드 두 번 저장, URL 없는 사진의 재정렬/명시적 삭제, Crew 세 원본 키 유형의 아이콘 crop/hotspot 반복 보존, 새 링크 첫 발급과 재저장 키 유지.

전체 **2,237개 / 68개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크 **35/35 통과**.

현재 초안·휴지통을 제외한 공개 공간 **5건/사진 13장**, Crew **3건/링크 5개**를 읽기 전용으로 집계했다. 사진의 URL·키 누락과 Crew 링크 키 누락·해당 접두사 사례는 **0건**이었다. 원문 URL·키·인증 정보를 출력하지 않았고 문서/에셋 쓰기도 하지 않았다. 현재 데이터에 자동 복구나 마이그레이션이 필요하다고 판단한 것은 아니다.

## 범위와 남은 점검

- 운영 CMS 저장·실제 사진 업로드·인증된 운영 브라우저 E2E·배포는 하지 않았다. 연결 테스트의 인증·읽기/쓰기 저장소·URL 투영·router refresh는 모의 구현이며, 자르기 UI는 대체했다. 실제 파일 복구·크롭 조작을 검증했다는 뜻은 아니다.
- URL이 없어진 원인이 실제 에셋 삭제라면 이번 수정이 파일을 복구하지는 않는다. 원본 행 정보를 보존하며, 필요하면 새 사진으로 교체해야 한다. 이미 과거 저장으로 빠진 행도 자동 복구하지 않는다.
- 사진 보존은 같은 원본 키로 서버 문서에서 행을 찾을 수 있는 경우의 정책이다. 키가 없는/잘못된 원본 행, 중복 키, 잘못된 배열 자료형까지 안전하게 편집·복구하는 범용 읽기 모델을 만든 것은 아니다.
- Crew 키 없는 예전 링크의 원본 아이콘 메타데이터 연결을 새로 추측하거나 재구축하지 않는다. 현재 확인한 링크에는 키 누락이 없었다.
- 이후 [설정 읽기 상태 점검](MANAGE_SETTINGS_READ_QA.md)에서 연락처·Studio 안내의 최초 설정·대체 표시·잘못된 원본 구분을 보완했다. 다른 상세 편집 화면의 모든 비정상 원본 처리를 완료했다는 뜻은 아니다. 정상 공개 디자인·운영 데이터·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
