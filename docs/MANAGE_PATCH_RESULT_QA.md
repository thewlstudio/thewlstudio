# 수정·휴지통·복원 성공 판정 점검

## 확인한 문제

- 단일 문서 패치의 `commit()` 응답을 검사하지 않아 null·다른 문서·잘못된 종류/버전도 성공으로 처리하고 캐시를 갱신할 수 있었다.
- 휴지통 이동/복원은 반환된 `trashed`가 요청과 달라도 성공으로 안내했다.
- 변경이 저장된 뒤 캐시 갱신만 실패해도 단순 실패로 안내해 재작업을 유도할 수 있었다. 요청 예외의 원문이 사용자에게 그대로 반환되는 경로도 있었다.
- 이력 복원 역시 잘못된 커밋 응답을 확인하지 않았고, 확인된 복원 뒤 캐시 실패를 구분하지 않았다.
- 실제 운영 손실 사례가 아니라 모의 저장소에서 재현한 결함이다.

## 반영 내용

- 서버 공통 `commitManagedPatch`는 단일 ID 패치 응답의 자체 `_id`·`_type`·`_rev`를 확인한다. ID/종류는 요청 대상과 일치해야 하고 버전은 비어 있지 않은 문자열이어야 한다.
- 네 콘텐츠 수정, 네 영역의 휴지통 이동/복원, 공통 설정/Studio 안내 수정, 여섯 영역의 이력 복원에 적용했다. 고정 설정을 처음 생성하는 경우에는 앞서 추가한 생성 응답 검사 후 같은 갱신 보호를 사용한다.
- 휴지통 작업은 반환된 불리언 `trashed`가 요청한 상태와 정확히 같아야 한다. `isActive`와 휴지통의 분리는 유지한다.
- 올바른 같은 버전 응답은 정상 무변경 작업일 수 있으므로 허용한다. 새 revision 발급을 강제하지 않는다. 기존 CAS revision 조건과 부분 패치·unset·원본 보존 규칙은 변경하지 않았다.
- 응답을 확인하지 못하거나 커밋 요청이 예외로 끝나면 “이미 반영됐을 수 있다”는 결과 확인 안내를 반환한다. 409는 기존 충돌 안내를 유지한다. API 오류 원문이나 응답 내용을 화면에 그대로 반환하지 않는다.
- 확인된 커밋 뒤 갱신이 실패하면 “변경은 완료됐지만 화면을 갱신하지 못했다”는 별도 안내를 반환한다. 모든 성공 캐시 처리는 응답 검사 뒤에만 수행한다.
- 자동 재요청·재조회·추가 패치·원본 복구/삭제는 하지 않는다. 폼의 입력/dirty를 유지하고 삭제·복원 버튼의 성공 알림/이동도 실행하지 않는다.
- 기존 정상 테스트의 저장소 mock은 문서 ID/종류/버전과 요청한 변경을 포함하는 SDK 문서 응답으로 맞췄다. 오류를 통과시키도록 검증을 낮추지 않았으며 기존 캐시 경로와 충돌 기대값은 유지했다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 설치된 Sanity 클라이언트의 단일 `Patch.commit()` 기본값이 `returnFirst: true`·`returnDocuments: true`인 것도 확인했다. 여러 문서 트랜잭션의 기본 응답은 다르므로 이 검사에 섞지 않았다.

## 검증

새 회귀 테스트 **216개**를 추가했다.

- 실제 서버 액션 176개: 수정/설정/삭제/복원 14개 경로의 비정상 응답·다른 종류/버전·요청 예외·캐시 실패·정상/같은 버전 성공·409, 휴지통 상태 불일치 8개.
- 이력 복원 액션 30개: 여섯 영역의 null/다른 ID/빈 버전, 복원 확인 후 캐시 실패, 커밋 예외 시 단일 호출.
- 실제 조회→폼→액션 5개: 네 콘텐츠에서 결과 불명 시 입력·dirty·원본 유지, 실제 모의 저장 뒤 캐시만 실패하면 저장된 문서와 별도 안내를 유지하고 자동 재저장/refresh하지 않음.
- 버튼 DOM 5개: 네 삭제 확인창과 복원 버튼이 결과 불명 상태를 성공 알림/이동으로 바꾸지 않음.
- 인증·외부 저장소·라우터는 모의 구현이다. 실제 CMS 패치·업로드·인증된 브라우저 E2E는 하지 않았다.

전체 **4,029개 / 99개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

## 범위와 한계

- 반환 문서의 식별 정보와 휴지통 상태를 확인하는 작업이다. 모든 저장 필드/중첩 값의 의미를 응답에서 다시 검증하거나 별도 읽기로 서버 상태를 재확인하는 새 프로토콜은 아니다.
- 결과 불명은 미저장을 뜻하지 않는다. 캐시 갱신 실패도 실제 저장을 취소하지 않는다. 자동 롤백은 하지 않으며 일부 화면 캐시가 기존 값으로 남을 수 있다.
- 작업자가 확인 없이 수동 재요청하는 것을 완전히 막거나 요청 멱등성을 추가하지 않았다. 안내대로 새 탭에서 현재 내용을 먼저 확인해야 한다.
- 순서 변경은 여러 문서 트랜잭션 응답을 사용하므로 이번 단일 문서 검증에서 제외했다. 별도 점검 대상이다.
- 공개 디자인·스키마·환경변수·의존성은 변경하지 않았다. 운영 데이터 저장·실제 업로드·커밋·배포도 하지 않았다.
