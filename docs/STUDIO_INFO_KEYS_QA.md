# Studio 안내 원본 키 왕복 점검

## 재현한 문제

서비스·장비·멤버십의 원본 `_key`가 다음 세 경로에서 사라졌다.

1. 관리 페이지의 GROQ 투영이 배열 `_key`를 조회하지 않았다.
2. 공개 화면용 `mergeInfo`는 내용만 변환하므로 원본 키를 반환하지 않았다.
3. 폼이 카드용 `svc-0`, `eq-0`, `mem-0`을 저장용 `_key`로 보냈다.

내용을 바꾸지 않아도 첫 저장에서 원본 키가 교체되고, 순서를 바꾼 뒤 재조회하면 순번 키가 다른 항목에 붙을 수 있었다. 조회·폼 직렬화 테스트 **6개**를 먼저 작성했으며 수정 전 모두 실패했다. 운영 문서를 실제로 저장해 재현하지는 않았다.

## 반영 내용

- 관리 페이지의 세 배열 투영에 `_key`를 추가했다. 기존 revision 조회·로그인 차단은 유지한다.
- `StudioInfoForManage`와 `mergeInfoForManage`를 추가했다. 내용·기본값·빈 배열 규칙은 기존 `mergeInfo`와 같게 하고 같은 원본 행의 비어 있지 않은 문자열 키만 관리자 모델에 보존한다.
- 공개 화면은 계속 기존 `mergeInfo`를 사용한다. 공개 모델에 `_key`를 추가하거나 표시값·문구·레이아웃을 바꾸지 않았다.
- 폼의 카드·React·접기/펼치기·입력 ID에는 기존 화면 내부 `key`를 사용하고, 저장 JSON에는 별도의 원본 `_key`를 사용한다. 원본 키에 공백·한글·기호가 있어도 DOM ID에 직접 넣지 않는다. 다른 배열의 같은 원본 키도 접기/펼치기 상태를 공유하지 않는다.
- 원본 키가 없는 기본 항목이나 새로 추가한 행은 `_key`를 보내지 않는다. 화면 내부 `new-…` 키도 서버로 보내지 않는다. 서버가 처음 저장할 때 UUID 일부를 발급하고, 성공 후 재조회한 실제 키가 다음 편집 기준이 된다.
- 안내 저장 액션은 명시적으로 받은 비어 있지 않은 문자열 `_key`를 정확히 유지한다. 기존 키가 `new-`로 시작하더라도 원본 키와 임시 화면 키를 혼동해 재발급하지 않는다. 키가 없거나 빈 문자열이면 기존 공통 도우미로 발급한다. 다른 영역의 임시 키 규칙은 바꾸지 않았다.
- 같은 배열의 중복 원본 키는 계속 저장 오류로 반환한다. 자동 병합·삭제·키 교체를 하지 않는다. UI 키가 분리돼 있으므로 중복 원본이 있더라도 카드 입력 자체는 별개의 항목으로 유지한다.
- JSON 구조·필수 값·길이/개수·중복 키 검사, 인증·revision 조건·캐시 갱신, 저장 실패 후 입력 보존은 유지한다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 일반 고정 문서 저장 도우미의 읽기/쓰기 순서나 concurrency 정책은 변경하지 않았다.

## 검증

새 테스트 **24개**를 추가했다.

- 관리 모델 **9개**: 세 배열 원본 키 보존과 공개 모델 불변, 원본 없음/필드 없음의 기본값, 명시적 비우기, null 행 제외 후 내용·키 대응, 배열 간 같은 키·특수문자 키, 입력 불변성.
- 관리 페이지 **3개**: 실제 페이지를 호출하고 GROQ에 `_key`가 없는 경우 응답에서 키를 빼는 모의 저장소로 세 배열의 조회·폼 전달을 검사한다. 모델만 바꾸거나 쿼리만 바꿔서는 통과하지 않는다.
- 실제 폼 직렬화 **3개**: 세 배열의 원본 키를 화면 내부 순번 키로 바꾸지 않는다.
- 실제 폼→실제 액션→모의 저장소→새 revision 재렌더 **9개**: 세 배열 각각 재정렬·두 번 저장·삭제·새 행 추가·추가 후 재저장, 배열 간 같은 키의 카드/DOM ID 독립성, 키 없는 기본 항목 첫 발급, 문서 최초 생성 후 키 유지, 세 배열의 중복 키 오류와 명시적 삭제 후 재시도.

전체 **2,006개 / 64개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크 **35/35 통과**.

공개 고정 안내 문서를 읽기 전용으로 조회했다. 서비스 **2개**, 장비 **3개**, 멤버십 **3개**의 원본 키가 새 관리 모델에서 모두 유지됐고, 미지정·중복 키는 없었다. 키를 제외한 표시값은 기존 공개 모델과 동일했다. 원문 키·문구·인증 정보를 로그에 출력하지 않았으며 CMS 쓰기는 하지 않았다.

## 범위와 한계

- 운영 CMS 쓰기·인증된 운영 브라우저 저장 E2E·배포는 하지 않았다. 실제 폼/액션 검증의 저장소·인증·router refresh는 모의 구현이다. 새 revision 재렌더는 해당 조건을 재현한 것이며 네트워크 전송이나 Vercel 캐시 E2E 전체를 대체하지 않는다.
- 이미 과거 저장으로 바뀌거나 사라진 원본 키를 자동 복구하지 않는다. 현재 읽은 원본부터 보존한다. 키가 없는 기존 행은 다음 저장 때 새 키를 받는다.
- 이 작업은 Sanity의 모든 키 문자 규칙·길이 한계를 검사하는 기능이 아니다. 기존 문자열 키를 임의로 정규화하지 않는 정책이며 새 행은 기존 서버 UUID 발급 방식을 쓴다.
- 배열 객체의 알 수 없는 확장 메타데이터까지 모두 유지하는 범용 무손실 편집기를 만든 것은 아니다. 공개 내용 정리 규칙과 지원 필드는 그대로다.
- 다른 영역의 본문 구조 검증·원본 메타데이터 왕복은 별도 점검 대상이다. 정상 콘텐츠 디자인·운영 데이터·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
