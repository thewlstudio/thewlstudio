# 생성 결과 확인·재시도 안내 점검

## 확인한 문제

- 네 생성 액션과 강사 복제는 `client.create()`의 `_id`를 검증하지 않고 수정 주소/성공 결과에 사용했다. 고정 문서의 최초 생성도 응답을 확인하지 않았다.
- 문서는 생성됐지만 뒤따르는 캐시 갱신만 실패한 경우에도 단순 실패처럼 표시할 수 있었다. 사용자가 다시 추가해 중복을 만들 위험이 있었다.
- 공통 클라이언트 처리기는 예외는 잡았지만 null·잘못된 `ok`·오류 객체 등 비정상 반환값은 그대로 넘겼다. 폼이 깨지거나 복제 버튼이 잘못된 새 주소로 이동할 수 있었다.
- 실제 운영 생성/중복 사례를 확인한 것이 아니라 모의 저장소에서 재현한 결함이다.

## 변경 사항

- 서버의 `createManagedDocument`는 한 번의 생성 응답에서 공개 문서 ID 형식, 요청한 `_type`, 비어 있지 않은 `_rev`를 확인한다. 고정 문서는 요청한 ID와 일치해야 한다. 초안/릴리스 ID·경로 문자는 거부한다. 강사 복제 결과가 원본 ID인 경우도 새 문서 성공으로 처리하지 않는다.
- 예상하지 못한 생성 응답이나 전송 예외는 실제 생성 여부를 단정하지 않는다. 이미 추가됐을 수 있으므로 재추가 전에 새 탭에서 목록을 확인하도록 안내한다. 문서를 다시 만들거나 지우는 자동 복구는 하지 않는다.
- 409 충돌은 기존의 안전한 충돌 안내를 유지한다. 생성 API 오류 원문은 사용자에게 그대로 반환하지 않는다.
- 생성 응답이 확인된 뒤 캐시 갱신이 실패하면 “추가는 완료됐지만 화면을 갱신하지 못했다”는 별도 안내를 돌려준다. 재추가를 권하지 않으며 정상 성공 이동도 하지 않는다.
- `callManageAction`은 자체 `ok` 불리언, 오류 문자열, 선택적 필드 오류 목록의 형식을 확인한다. 잘못된 값은 기존의 처리 결과 불명 안내로 바꾸며 다시 호출하지 않는다. 정상 성공/필드 오류 객체와 Next redirect/notFound 제어 신호는 기존대로 유지한다.
- 복제 버튼은 추가 성공 정보의 새 ID도 검사한 뒤 이동한다. 기존 같은 탭 잠금·현재 경로 확인·중복 클릭 방지는 유지한다.
- 정상 응답 테스트 fixture는 실제 기본 `create()` 계약에 맞게 `_id`·`_type`·`_rev`를 반환하도록 보완했다. 잘못된 응답을 정상으로 인정하도록 검증을 느슨하게 하지 않았다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 설치된 Sanity 클라이언트의 `_create` 구현(`returnFirst: true`, `returnDocuments: true`)과 응답 정리 코드도 직접 확인했다. 외부 저장을 실행해 응답을 만든 것은 아니다.

## 검증

새 테스트 **153개**를 추가했다.

- 실제 생성/복제/고정 문서 액션 134개: null·불완전한 응답·잘못된 ID/종류/revision·다른 고정 ID·원본과 같은 복제 ID, 정상 응답, 전송 실패 시 단일 호출, 생성 후 캐시 오류의 별도 안내와 성공 이동/캐시 미실행.
- 공통 통신 처리 10개: 비정상 반환값과 성공 추가 정보 검사, 정상 객체 보존, 오류 응답에는 성공 검사를 적용하지 않음.
- 복제 버튼 DOM 6개: 잘못된 새 ID로 이동하지 않고 결과 확인 안내 표시.
- 실제 폼/공통 훅 3개: 비정상 저장 응답에도 입력·dirty·화면 유지, 자동 반복·refresh 없음. 저장 액션은 모의 응답이다.
- 인증·외부 저장소·라우터는 모의 구현이다. 실제 생성/업로드/인증된 브라우저 E2E는 하지 않았다.

전체 **3,813개 / 98개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

## 범위와 한계

- 중복 생성의 완전한 방지나 요청 멱등성을 구현한 것은 아니다. 사람이 목록 확인 없이 다시 누르거나 다른 브라우저에서 재요청하면 중복이 생길 수 있다. 고유 요청 ID·서버 상태 저장·고정 생성 ID·결과 조회/재개 프로토콜은 별도 설계가 필요하다.
- 응답이 없거나 잘못됐다고 서버에 문서가 없다는 뜻은 아니다. 에셋/문서를 자동 삭제하거나 확인되지 않은 ID를 추측해 덮어쓰지 않는다.
- 생성 후 캐시 갱신 실패 시 문서는 유지되며 일부 화면이 기존 캐시로 남을 수 있다. SDK/네트워크 전체 재시도 정책은 변경하지 않았다. 이번 단일 호출 검증은 애플리케이션 코드/모의 저장소 수준이다.
- 수정/삭제 등 다른 서버 액션의 모든 오류 원문 처리나 모든 저장 응답까지 새로 검증한 작업은 아니다. 공통 클라이언트 응답 형식 검사는 모든 호출에 적용된다.
- 공개 디자인·스키마·환경변수·의존성은 변경하지 않았다. 운영 데이터·실제 업로드·커밋·배포도 변경하지 않았다.
