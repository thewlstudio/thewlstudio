# 본문 추가 필드 재작성 손실 보호

## 재현한 문제

- Works·Crew의 일반 편집 형식은 제출된 값으로 객체를 다시 만든다. 원본에 편집기가 다루지 않는 필드가 있으면 제목·이름 등 다른 값을 저장할 때 함께 빠질 수 있었다.
- 최상위뿐 아니라 크레딧·트랙·연도·경력·수상·활동의 중첩 객체에도 같은 위험이 있었다. 예를 들어 새 수상 항목의 `desc`나 중첩 객체의 `_type`은 현재 제출/저장 형식에 포함되지 않는다.
- 처음 작성한 회귀 테스트 **23개 중 22개가 수정 전 실패**했다. 서버 원본 전체를 유지하는 오디오/미지원 본문은 기존에도 안전했다. 실제 운영에서 손실이 발생한 것으로 확인한 것은 아니다.

## 반영한 정책

- 알 수 없는 필드를 임의로 병합하거나 클라이언트가 보낸 추가 값을 새로 받아 저장하지 않는다. **유지하려는 원본에 재작성으로 사라질 필드가 있으면 저장을 차단**하는 보수적 정책을 적용했다.
- 서버 전용 `body-extra-fields.ts`가 실제로 재작성하는 필드와 하위 객체 배열을 정의한다. Works 일반 6종과 Crew 일반 6종을 검사한다. 원본을 통째로 유지하는 오디오·미지원 종류는 이 재작성 검사 대상이 아니다.
- 원본의 같은 키로 제출된 항목을 찾는다. 키가 없거나 부모를 연결할 수 없으면 추가 정보를 새 행에 붙이거나 삭제됐다고 추측하지 않는다. 같은 키의 종류 변경으로도 하위 추가 정보 보호를 피하지 않는다.
- 추가 필드의 값이 null·빈 문자열·false처럼 비어 보여도 임의로 지우지 않는다. 중첩 `_type` 등 현재 저장 형식에서 빠지는 메타데이터도 보호 대상이다.
- 검사는 기존 자료형·한도 검사 뒤, **사진 업로드나 문서 패치 전**에 실행한다. 뒤쪽 항목의 문제로 앞쪽 사진이 먼저 업로드되지 않도록 했다. Crew 링크 아이콘·대표 사진도 이 검사 뒤에만 처리된다.
- 오류는 기존 `blocks`/`sections` 필드 안내로 연결한다. 고정된 묶음 이름과 원본 확인용 `/admin` 경로만 안내하며, 원문 값·추가 필드 이름을 오류에 넣지 않는다. 폼 입력·미저장 상태는 유지한다.
- 제출 목록에서 유효한 원본 키가 빠진 경우는 기존 전체 배열 교체 계약에 따라 삭제로 처리한다. 일반 블록의 삭제 기능을 없애지 않았다. 반면 항목을 남겨 둔 채 칸만 비우면 추가 정보가 자동 정리되지 않도록 저장을 차단한다.
- 본문 JSON 자체를 생략한 기존 기본 정보 저장은 본문을 패치하지 않으므로 계속 허용한다. 일반 관리 폼은 본문 전체를 제출하므로 해당 오류가 나면 `/admin`에서 원본을 확인해야 한다.
- 인증·본문 한도·원본 키·미디어 참조·revision 조건·캐시 갱신은 변경하지 않았다. 정상 본문과 공개 디자인에도 변경이 없다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 판별에는 액션이 조회한 서버 원본을 사용하고 클라이언트의 원본 주장을 신뢰하지 않는다.

## 검증

새 테스트 **44개**를 추가했다.

- 저장 정리 함수 **38개**: 일반 형식·중첩 행의 추가 정보, 미디어 필드가 잘못된 종류에 붙은 경우, 원본 종류 변경·키 미지정·빈 값·특수 필드 이름·원본 불변성·원문 미노출·업로드 전 거부·명시적 삭제·원본 보존 종류/새 입력과의 구분.
- 실제 저장 액션 **4개**: 두 영역에서 추가 필드 오류 시 업로드·패치·캐시 갱신 없음, 본문 JSON 생략 시 원본 유지. 저장소는 모의 구현이다.
- 실제 조회 페이지→폼→액션 **2개**: 저장 오류 뒤 입력과 dirty 상태, 오류 연결 대상, 서버 문서/revision 유지와 자동 refresh 미실행. 인증·외부 저장소·라우터는 모의 구현이다.
- 기존 한도 테스트의 원본 fixture가 모든 블록에 `image`와 `audioFile`을 붙이던 부분은 실제 사진/오디오 종류에만 붙이도록 맞췄다. 한도 초과·경계값의 기대 결과는 유지하고, 다른 종류의 미디어 필드가 실제 원본에 있으면 거부하는 별도 회귀 테스트를 추가했다.

전체 **3,115개 / 92개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크도 **37/37 통과**했다.

공개 Crew **3건**, Works **8건**을 읽기 전용으로 조회해 메모리 안에서만 실제 편집 모델 왕복과 저장 정리를 적용했다. 거부 **0건**, 속성 나열 순서를 정규화한 본문 값/배열 순서 변화 **0건**, 업로드 콜백 실행 **0회**였다. 원문·문서 ID·인증 정보를 출력하거나 실제 문서/에셋을 쓰지 않았다.

## 범위와 한계

- 추가 필드를 편집할 수 있게 만든 작업이 아니라 **손실 가능한 재작성을 막는 보호**다. 유용한 메타데이터여도 현재 저장기가 다루지 않는 필드라면 차단한다. 원본 확인이나 명시적인 새 형식 지원이 필요하다.
- 명시적 삭제의 판정은 제출된 전체 배열의 키에 따른 기존 계약이다. 낡거나 잘못된 클라이언트가 키 자체를 빠뜨린 경우와 사용자의 의도까지 구분하는 새 삭제 확인 프로토콜은 추가하지 않았다.
- 사진의 crop/hotspot처럼 기존에 통째로 보존하는 객체 내부와 미지원 본문 전체를 재귀 해석하거나 정리하지 않는다. 모든 잘못된 원본 자료형을 복구하는 기능도 아니다.
- 새 편집 필드를 지원할 때는 이 필드 정의와 실제 저장기·편집 모델을 함께 갱신하고 왕복 테스트를 추가해야 한다. 보호 검사를 끄거나 원본 필드를 임의 제거해 우회하지 않는다.
- 실제 운영 저장·업로드·인증된 브라우저 E2E·배포는 하지 않았다. 현재 공개 11건은 차단 대상이 아니었으며 정상 디자인·스키마·환경변수·의존성·커밋도 변경하지 않았다.
