# 저장 폼의 새로고침 실패·기준값 보호 점검

## 확인한 문제

- 여섯 관리 폼은 공통 `useManagedFormAction`에서 성공 후 refresh를 시작한다. 전환 콜백의 동기 오류를 처리하지 않아 모의 테스트에서 폼이 오류 경계로 바뀌고 입력에 접근하지 못했다.
- 성공한 저장과 최신 기준값을 다시 읽는 일은 다르다. 서버 키·사진 참조·정규화된 값을 못 받은 상태에서 재저장하거나 `변경 버리기`로 예전 props를 다시 마운트하면 잘못된 재전송/기준값 복구로 이어질 수 있었다.
- 늦은 응답에서는 refresh만 생략하고 액션 결과는 반영해, 주소가 달라진 뒤에도 성공 표시나 dirty 해제가 발생할 수 있었다.
- 보조 체크리스트 기록도 저장 성공 처리에 포함돼, 손상된 브라우저 기록에서 예외가 나면 기준값 갱신까지 막을 수 있었다.
- 모의 액션·라우터로 재현했으며 실제 운영 데이터 손상을 확인한 것은 아니다.

## 반영 내용

- refresh 동기 오류는 같은 전환 콜백에서 처리한다. 유효한 저장 성공 뒤 오류를 확인하면 “저장은 완료됐지만 최신 내용을 불러오지 못했어요”라고 안내하고 폼을 유지한다. Next 제어 신호는 `unstable_rethrow`로 전달한다.
- 실패 상태를 당시 revision에 연결해 공통 훅에 보관한다. 그 기준값을 사용하는 동안 저장 버튼을 다시 눌러도 서버 액션을 호출하지 않는다. 사진·배열 입력을 다시 업로드/재작성하는 요청으로 넘어가지 않는다.
- 같은 상태에서 `변경 버리기`는 폼 키를 바꾸지 않고 입력을 유지하며 실행하지 않았음을 안내한다. 입력은 따로 보관하고 새 탭에서 현재 내용을 확인해야 한다.
- 새 revision props를 받으면 이전 실패 상태는 적용하지 않는다. 기존 폼 키/리마운트 구조로 서버의 최신 기준값을 반영하고 저장·버리기를 다시 허용한다. 임의로 입력 일부만 기준값으로 복사해 서버 정규화·키를 추측하지 않는다.
- 기준값을 못 받은 동안에는 입력 손실 방지를 위해 dirty/미저장 보호를 보수적으로 유지한다. 이는 실제 저장이 안 됐다는 뜻이 아니며 저장 완료 사실은 별도 안내한다. 영구 pending이나 전역 잠금을 남기지 않는다.
- 화면을 떠난 뒤 응답은 이전 결과를 유지해 새 성공/실패 표시나 dirty 해제를 만들지 않는다. 보조 체크 기록의 예외는 저장 결과·refresh를 깨뜨리지 않도록 격리한다.
- 여섯 폼의 정상 UI·서버 저장·스키마·환경변수·의존성은 바꾸지 않았다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-router.md`와 `unstable_rethrow.md`를 읽었다. refresh 호출을 최신 데이터 반영이 완료된 Promise로 취급하지 않는다.

## 검증

새 DOM 테스트 **27개**를 추가했다.

- 여섯 폼 각각 4개: refresh 동기 오류 시 폼/입력/변경 보호 유지, 오래된 기준값으로 버리기 차단, 서버 재저장 호출 차단과 잠금 정상 해제, 새 revision을 받은 뒤 정상 저장/최근 저장값으로 버리기. 합계 24개.
- 늦은 성공/실패 응답 2개에서 입력·dirty 유지와 refresh/새 결과 표시 없음.
- 손상된 실제 테스트용 localStorage 체크 기록 1개에서 저장/refresh 유지와 오류 경계 진입 없음.
- 첫 24개는 보완 전 실패하는 것을 재현했고 보완 후 통과했다. 기존 서버 발급 배열 키·사진 참조 왕복, 정상 버리기·인증/통신 오류·공유 잠금도 회귀 확인했다.
- 전체 **4,610개 / 107개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

## 범위와 한계

- 액션·라우터는 모의 구현이다. React DOM·폼·보호 훅은 실제 코드이며 새 revision은 서버 재응답을 모사해 주입했다. 운영 저장·업로드·커밋·배포 또는 인증된 브라우저 E2E는 수행하지 않았다.
- 이번 보호는 유효한 성공 응답 뒤 **브라우저 refresh 호출의 동기 오류를 확인한 경우**에 적용한다. 호출 후 비동기 실패나 오류 없이 예전 데이터가 다시 온 모든 경우를 감지하는 새 readback 프로토콜은 아니다.
- 최초 점검에서는 서버의 `ok: false` 문구로 저장 사실을 추측하지 않았다. 이후 [서버 저장 확인 상태 점검](MANAGE_COMMITTED_SAVE_QA.md)에서 명시적 `committed` 표시로 같은 기준값 보호를 연결했다. 표시 없는 응답은 여전히 문구로 추정하지 않는다.
- 버튼 자체를 영구 비활성화하거나 다른 관리 작업을 잠그지 않는다. 실패 revision의 폼에서 재저장 전송/버리기만 보류한다. 새 revision을 못 받으면 입력을 보관한 뒤 새 탭이나 새 페이지 진입으로 확인해야 한다. 같은 revision의 정상 무변경 응답을 별도 재조회 완료로 증명하지 않는다.
- 새로고침/탭 종료를 넘어 입력을 영구 보관하는 기능은 아니다. 실제 새 페이지 진입 전에 필요한 입력을 따로 보관해야 한다.
