# 관리자 이미지 업로드·보존 점검

## 확인한 문제

- 브라우저 사진 준비 함수의 최종 상한은 2,800,000바이트인데 서버 도우미는 10MiB를 허용하고 있었다. 실제 HTTP 요청에는 별도로 Next의 4mb 제한이 있으므로, 10MiB가 그대로 운영 서버에 전송됐다는 뜻은 아니다.
- 강사 업로드만 별도 구현되어 검증과 안내 문구가 중복돼 있었다.
- 서버 코드가 폼 값을 `File`로 단언한 뒤 `.type.startsWith()`를 호출했다. 파일 자리에 문자열이 오면 내부 TypeError가 운영자에게 반환될 수 있었다.
- 이름이 있는 빈 파일도 미선택 파일처럼 생략해, 교체하려던 사진이 바뀌지 않아도 성공으로 처리할 수 있었다.
- Crew 링크의 기존 아이콘을 그대로 유지해도 에셋 참조만 다시 조립해 crop·hotspot·추가 메타데이터가 사라졌다. 실제 저장 액션의 모의 문서로 재현 후 수정했다.

## 반영 내용

### 제한과 검사 경계

| 단계 | 적용 기준 | 역할 |
| --- | --- | --- |
| 사진 한 장 | **2,800,000바이트(2.8MB)** | 브라우저 준비 함수와 서버 업로드 도우미가 공유 |
| 이미지 폼 전체 | **3,800,000바이트 예산** | 파일·UTF-8 텍스트·multipart 여유분을 합산해 브라우저와 서버에서 검사 |
| Next 요청 본문 | 기존 **4mb** 유지 | 앱 코드 진입 전의 별도 전송 제한 |

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md`를 읽었다. 전체 예산은 보수적 추정이며 실제 wire 바이트와 동일하다는 보장은 아니다. Next 본문 한도나 허용 Origin 설정을 넓히지 않았다.

- 장당 정책·문구를 `manage-image-policy.ts`에 모았다. 기존 전체 폼 계산은 동작을 유지한 채 `manage-form-payload.ts`로 옮겨 서버에서도 사용한다. 이전 클라이언트 import 경로는 재수출로 유지한다.
- 강사·Crew·Works·Studio 공간의 **저장/생성 액션 8개**에서 인증 → 전체 용량·모든 알려진 이미지 입력 검사 → 저장소 접근 순서를 적용했다. 다른 설정 폼이나 순서 변경 액션에 이미지 검사를 넣지는 않았다.
- 같은 이름의 반복 파일도 전체 예산에 합산한다. 검사하는 동안 파일 바이트를 읽거나 업로드하지 않는다.
- 선택하지 않은 입력의 `이름="", 크기=0` File은 기존처럼 무시한다. 선택한 빈 파일, File 아닌 값, 이미지 MIME이 아닌 파일, 장당 상한 초과는 안내 오류로 거부한다.
- 업로드 도우미 자체도 같은 검사를 수행하며 강사도 이 도우미를 사용한다. 기존 이미지 형식을 새로운 allowlist로 제한하지 않았다.
- 업로드/바이트 읽기 오류는 한국어 안내로 반환한다. 새 공통 도우미에서는 API 원문·파일명·요청 헤더 대신 숫자 상태 코드만 로그에 남기며 자동 재시도하지 않는다.
- Crew 프로필 도움말·사용 안내·운영 가이드의 장당 제한을 실제 값인 2.8MB로 맞췄다.

### 이미지 보존

- 같은 Crew 링크 키와 같은 아이콘 에셋이면 **서버 원본**의 crop·hotspot·추가 메타데이터를 유지한다. 클라이언트가 보낸 crop 객체를 신뢰하는 방식은 아니다.
- 다른 에셋으로 선택을 바꾸거나 새 파일을 올리는 경우 이전 사진의 crop을 새 사진에 옮기지 않는다.
- 기존 Works 본문 사진·Studio 사진의 서버 발급 키와 참조 보존 동작은 유지한다.
- 새 업로드가 실패하면 문서 패치를 실행하지 않아 기존 이미지와 revision이 유지된다. 이번 수정은 이미 사라진 과거 crop 정보를 자동 복구하는 작업은 아니다.
- 기존 Sanity 에셋의 용량을 검사해 삭제하거나 다시 저장하지 않았다. 2.8MB 제한은 새로 제출하는 파일에 대한 것이다.

## 검증

새 회귀 테스트 **92개**를 추가했다.

- 공통 서버 업로드 **31개**: File/미선택/빈 파일, MIME·용량 경계, 바이트 읽기 전 차단, 이미지 엔드포인트 인자, 오류 안내와 단일 전송, 전체 폼의 중복 이름·순서·불변성. Node의 실제 Request/FormData multipart 직렬화·역직렬화 뒤 File 호환도 확인했다.
- 실제 저장/생성 액션 **48개**: 8개 액션 각각 문자열·빈 파일·비이미지 MIME·장당 초과·전체 초과·인증 우선 처리. 거부 시 쓰기 클라이언트·업로드·문서 쓰기·캐시 갱신이 호출되지 않음을 확인했다.
- 실제 모의 문서 **10개**: Crew 아이콘 원본 메타데이터 보존·다른 에셋으로 교체, 강사 3종 사진·Crew 대표/아이콘·Works 커버/본문·Studio 사진의 업로드 실패 후 문서 보존.
- 브라우저 사진 준비 함수 **3개**: 빈 파일과 2.8MB 경계. 기존 준비 경합·취소·크롭·폼 오류 후 입력 보존 테스트도 유지했다.

전체 **1,445개 / 58개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 최종 로컬 서버 경로 스모크도 **35/35 통과**했다. 확인용 서버는 종료했다.

## 범위와 한계

- 테스트는 Sanity 쓰기/API 업로드를 대체했다. 모의 파일 바이트에는 실제 이미지가 아닌 검증용 데이터도 포함된다. 실제 운영 사진 업로드나 Next Server Action의 전체 multipart E2E를 검증했다는 뜻은 아니다.
- MIME 선언을 신뢰할 수 있는 이미지 내용 검증으로 간주하지 않는다. 실제 이미지 처리 성공 여부는 [Sanity 이미지 업로드 API](https://www.sanity.io/docs/http-reference/assets)가 판정하며, 지원하지 않는 형식·처리 불가 이미지에는 오류를 반환한다. 이번에 별도 이미지 디코더·백신·픽셀 수/압축 폭탄 검사를 추가하지 않았다.
- 브라우저 자동 축소는 기존 JPEG/PNG/WebP 처리 방식과 자원 정리를 유지한다. 다른 형식이나 직접 업로드하는 Crew 맞춤 링크 아이콘은 큰 파일을 자동으로 줄이지 않을 수 있으므로 작은 이미지를 준비해야 한다. 서버 제한은 이 입력에도 적용된다.
- 사전 검사로 판별 가능한 오류는 업로드 전에 막지만, 여러 파일 중 뒤쪽의 **실제 디코딩/네트워크/API 오류**로 실패하면 앞서 업로드한 미참조 에셋이 남을 수 있다. 기존에 공유되는 에셋을 잘못 지우지 않도록 자동 삭제는 하지 않았다.
- 파일은 전송돼도 문서 커밋이 실패할 수 있다. 네트워크가 결과를 알리지 못한 경우에는 자동 재시도하지 않고 확인 후 재시도하는 기존 정책을 유지한다.
- 본문 디자인·운영 사진·CMS 문서·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다. 새 외부 서비스나 임시 공개 테스트 라우트도 만들지 않았다.
