# 순서 변경 트랜잭션 응답 점검

## 확인한 문제

- 순서 변경은 `transaction.commit()`의 결과를 확인하지 않았다. null·다른 문서·일부 문서만 포함한 응답도 성공으로 처리하고 캐시를 갱신할 수 있었다.
- 커밋 확인 뒤 서버 캐시 갱신이 실패해도 일반 실패와 구분하지 못했다. 실제 변경이 없던 작업도 별도 구분하지 않았다.
- 목록 공통 훅은 비정상 액션 응답을 그대로 사용했다. 잘못된 `ok`나 오류 값이 성공 토스트/새로고침으로 이어질 수 있었다.
- 브라우저 `router.refresh()`의 동기 호출 오류도 저장 결과 불명과 혼동하거나 성공 표시 뒤에 처리할 수 있었다.
- 모의 저장소에서 재현한 문제이며 실제 운영에서 잘못된 순서 변경이 발생한 것으로 확인한 것은 아니다.

## 반영 내용

- 트랜잭션의 기본 반환 형식에 맞춘 서버 전용 `commitManagedOrder`를 추가했다. 자체 `transactionId`·`documentIds`·`results`를 검사하며 거래 식별자는 비어 있지 않은 문자열이어야 한다.
- 기대 문서는 전체 목록이 아니라 실제 패치를 보낸 항목만이다. 응답의 문서 집합은 누락·추가·중복 없이 일치해야 하고 `documentIds`와 `results`의 ID 순서도 같아야 한다. 서버가 요청과 다른 순서로 결과를 반환해도 두 목록과 집합이 일치하면 허용한다.
- 각 결과 작업은 단순 패치에 해당하는 `update`/`none`만 허용한다. 문자열로 강제 변환하지 않으며 `create`·`delete`·잘못된 객체·빈 슬롯도 거부한다.
- 강사·Crew·Studio의 화살표/드래그 여섯 경로에 적용했다. 커밋 응답 확인 뒤에만 기존 태그·경로 캐시를 갱신한다. 요청 예외와 비정상 응답은 결과 불명 안내로 바꾸며 자동 재시도·재조회·롤백 트랜잭션은 하지 않는다. 409 충돌 안내는 유지한다.
- 커밋이 확인된 뒤 갱신 실패는 “순서 변경은 완료됐다”고 구분한다. 패치할 항목이 없으면 커밋을 생략하고 응답도 요구하지 않는다. 이때 갱신만 실패하면 “순서는 변경하지 않았다”고 안내한다.
- 클라이언트 공통 순서 훅도 기존 액션 응답 검사를 재사용한다. 비정상 응답에는 확인 안내를 표시하며 성공 토스트/자동 재요청을 하지 않는다. 브라우저 refresh 동기 오류는 전환 콜백 안에서 처리하고 저장 확인 사실을 안내한다.
- 변경 항목만 패치하는 규칙·그룹 경계·revision 조건·잠금·최신 서버 목록 보존·공개 디자인은 유지한다. 기존 무응답 트랜잭션 mock은 SDK의 기본 결과 형식으로 맞췄으며 원래 저장/충돌 기대값은 유지했다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 설치된 Sanity의 트랜잭션 기본값 `returnDocuments: false`, `MultipleMutationResult` 타입과 `documentIds`를 `results`에서 만드는 구현도 확인했다. 단일 패치 문서 응답과 섞어 검사하지 않는다.

## 검증

새 테스트 **136개**를 추가했다.

- 실제 순서 액션 108개: 여섯 경로의 비정상 응답 12종·정상/none 결과·요청 예외·서버 캐시 실패·409, 세 드래그 경로의 무변경/무변경 후 갱신 실패. 잘못된 응답은 이미 반영됐을 수 있으므로 추가 트랜잭션으로 되돌리지 않는 것도 확인한다.
- 응답 검사 함수 18개: 정상 결과 순서 차이·원본 불변성, 잘못된 속성/작업/자료형·누락·빈 슬롯의 안전한 거부.
- 목록/훅 DOM 10개: 드래그/화살표의 비정상 반환값, 서버 캐시 실패 안내, 브라우저 refresh 동기 오류 시 성공 토스트·자동 재요청 없음과 잠금 해제.
- 인증·외부 저장소·라우터는 모의 구현이다. 실제 운영 트랜잭션·인증된 브라우저 E2E를 수행하지 않았다.

전체 **4,165개 / 101개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

## 범위와 한계

- 응답 형식과 요청 대상 집합을 검증하는 작업이다. 별도 조회로 저장된 모든 숫자를 다시 확인하거나 서버 트랜잭션 구현을 검증한 것은 아니다.
- 결과 불명은 미반영을 뜻하지 않는다. 오류 때 클라이언트는 기존 낙관적 배열을 복구할 수 있지만 서버 순서를 되돌리는 쓰기는 하지 않는다. 최신 서버 목록을 이미 받았으면 예전 배열로 덮어쓰지 않는다. 현재 상태는 안내대로 새로고침해 확인해야 한다.
- 서버 캐시 갱신 실패나 확인 뒤 브라우저 refresh 호출 오류는 저장을 취소하지 않는다. 비동기 렌더링/네트워크의 모든 후속 오류를 포괄적으로 잡는 새 오류 경계는 추가하지 않았다.
- 수동 반복 요청의 멱등성·새 전역 잠금·원본 목록의 모든 자료형 경계까지 새로 구현한 것은 아니다.
- 실제 순서/운영 데이터·업로드·커밋·배포는 변경하지 않았다. 디자인·스키마·환경변수·의존성도 변경하지 않았다.
