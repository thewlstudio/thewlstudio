# Studio 공간·안내 저장 한도 점검

## 재현한 문제

Studio 공간의 이름·설명·가격·특징·안내·사진과, Studio 안내 설정의 서비스·장비·멤버십·주차·이용 문구는 한도 초과분을 `slice`로 잘라 저장했다. 초과 입력을 거부해야 하는 회귀 테스트 **51개**를 먼저 만들었으며 수정 전 모두 실패했다.

예를 들어 공간 설명 5,001자는 5,000자로, 가격 필드 51자는 50자로, 장비 목록 51개는 50개로 저장되면서 성공을 반환할 수 있었다. 공간 생성과 수정이 같은 정리 함수를 사용하고 있었다.

## 반영 내용

서버 전용 `studio-content-limits.ts`에서 **모든 해당 필드·목록의 한도를 먼저 검사**하고, 초과하면 기존 필드 오류 형식으로 반환한다. 실제 저장 함수의 문자열·목록 자르기는 제거했다. 인증과 이미지 전송 용량 검사는 기존 순서를 유지한다.

| 대상 | 기존 한도 유지 |
| --- | --- |
| 공간 이름·한 줄 소개 | 각 300자 |
| 공간 설명 | 5,000자 |
| 공간 가격 | 10개, 라벨·금액·단위 각 50자 |
| 공간 사진 | 20개 |
| 공간 특징·안내 | 각 50개, 항목당 300자 |
| 안내 서비스·장비·멤버십 | 각 20개 |
| 서비스 제목·장비 제목 | 각 300자 |
| 서비스 금액·단위 | 각 100자 |
| 서비스 안내·장비 항목·편의시설 | 각 50개, 항목당 300자 |
| 멤버십 숫자 / 이름·영문 이름 / 금액 | 10자 / 각 100자 / 50자 |
| 멤버십 안내·이용 소개·주차 상세·CCTV 설명·이용 수칙 | 각 3,000자 |
| 주차 강조·주차 요금·CCTV 제목·강조 수칙 | 각 300자 |
| 주차 요금 라벨 | 50자 |

- 길이는 기존 JavaScript 문자열 길이(UTF-16 코드 단위) 기준이다. 시각적인 글자 수와 다를 수 있다.
- 공간은 기존처럼 CRLF를 LF로 통일한 후의 길이를 기준으로 검사하고, 저장할 때 앞뒤 공백을 제거한다. 안내 설정은 CRLF 정리와 앞뒤 공백 제거 후의 길이를 검사한다.
- 빈 줄·빈 가격 행 정리, 명시적으로 비운 안내 문자열·배열의 유지, 서비스·장비 제목과 멤버십 이름·금액의 필수 검사는 그대로 둔다. 한도는 비어 있는 항목을 포함한 제출 목록에 적용한다.
- 공간 한도 오류는 새 사진 업로드·문서 조회/패치·생성·캐시 갱신 전에 반환한다. 안내 한도 오류는 고정 문서 쓰기 전에 반환한다. 실제 토큰이 없는 환경에서도 쓰기 클라이언트 생성 단계에서 먼저 실패할 수 있다는 기존 구성상의 제한은 바꾸지 않았다.
- 공간 사진·가격·특징·안내의 Section에 포커스 가능한 고유 ID를 추가했다. 공유 Section은 선택적인 ID만 지원하도록 확장했으며, ID가 없는 기존 호출에는 Tab 정지점을 추가하지 않는다. 안내 편의시설에도 같은 이동 대상을 추가했다. 기존 서비스·장비·멤버십 묶음의 ID는 유지한다.
- 저장 오류 뒤 입력 JSON·기본 정보·dirty 상태를 유지하며, 오류 요약에서 해당 묶음으로 스크롤·포커스 이동한다. 자동 새로고침이나 초과분 자동 삭제는 하지 않는다.
- 안내 설정 서버의 기존 키 함수도 공통 도우미로 바꿔 긴 키를 40자로 자르지 않게 했다. 서비스·장비·멤버십 배열의 중복 키는 쓰기 전에 거부한다. 이는 관리 폼에서 서버 원본 키가 끝까지 유지됨을 보장하는 변경은 아니다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 인증·revision 조건·캐시 갱신·CMS 스키마·본문 용량 정책은 변경하지 않았다.

## 검증

새 회귀 테스트 **70개**를 추가했다.

- 실제 공간 저장·생성 **24개**: 12종 길이/개수에 대해 한도+1 오류와 정확한 경계값 보존. 초과 시 함께 보낸 사진도 업로드하지 않고 문서 쓰기·페이지 이동·캐시 갱신을 하지 않는다.
- 실제 안내 저장 **27개**: 일반 문구 10종과 서비스·장비·멤버십·편의시설 17종의 초과 차단 및 경계값 보존.
- 기존 정책·보조 경로 **14개**: CRLF·공백·빈 목록 처리, 필수 값, 안내 중복 키 3종과 긴 키 보존, 세 액션의 인증 우선 처리.
- 실제 폼 DOM **5개**: 공간 특징·가격·사진, 안내 편의시설·서비스의 오류 후 입력과 dirty 유지, 실제 묶음으로 포커스 이동, 자동 새로고침 없음. 실제 한도 검사와 모의 액션 응답을 조합했다.

전체 **1,725개 / 61개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크 **35/35 통과**.

공개 API에서 조회한 현재 공간 **5건**과 고정 안내 설정 **1건**에 실제 한도 검사를 읽기 전용으로 적용했으며, 거부된 항목은 **0건**이었다. 문서 원문이나 인증 정보는 출력하지 않았다.

## 범위와 남은 점검

- 운영 CMS 저장·실제 사진 업로드·인증 브라우저 저장 E2E·배포는 하지 않았다. 테스트는 모의 Sanity와 검증용 파일 바이트를 사용한다.
- 이미 한도를 넘는 원본이 있으면 일부 기본 정보만 바꾸더라도 전체 제출 저장은 차단될 수 있다. 입력을 임의로 삭제하지 말고 원본을 확인해 정책 변경이나 `/admin` 편집을 검토해야 한다. 현재 조회한 6건에서는 한도 초과가 없었다.
- 이 작업 당시 범위는 길이·개수와 안내 배열 키 검사였다. 이후 [Studio JSON 구조 점검](STUDIO_JSON_SHAPE_QA.md)에서 자료형·필수 필드 누락과 공간 `listsJson`의 비객체 입력 처리도 보완했다. 이 문서의 테스트 수는 한도 점검 당시 기준이다.
- 이 점검 당시 남아 있던 안내 편집기의 순번 기반 저장 키 문제는 이후 [안내 키 보존 점검](STUDIO_INFO_KEYS_QA.md)에서 조회·관리 모델·폼 직렬화까지 보완했다.
- 정상 콘텐츠 디자인·운영 문서·에셋·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
