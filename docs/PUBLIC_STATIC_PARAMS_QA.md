# 빌드 시 공개 상세 주소 생성의 응답 경계

## 확인한 문제

- `publicStaticParams`는 SDK가 항상 `{ slug }[]`를 준다고 가정해 `rows.map(row => row.slug)`를 호출했다. 목록에 `null`/`undefined`가 섞이면 그 행만 제외하지 못하고 주소 생성 전체가 중단됐다.
- 상속된 배열 슬롯·상속된 slug나 배열 객체에 붙은 slug도 주소 후보로 쓰일 수 있었다. 정상적인 JSON 응답은 이런 상속 구조를 만들지 않지만 경계 검증 없이 자료형만 믿지는 않도록 보강했다.
- 기존 비정상 slug/중복 제외 정책과 달리, 잘못된 행의 구조는 검사하지 않았다. 가상 응답으로 이 문제를 확인했으며 운영 CMS를 바꾸어 재현하지 않았다.

## 수정과 유지한 정책

- 두 `generateStaticParams`의 SDK 조회를 `unknown`으로 받아 공통 함수에서 실제 자료형을 검사한다. 조회 쿼리와 `includeHidden: false`는 그대로다. 미리보기 쿠키나 쓰기 토큰을 사용하지 않는다.
- 입력이 배열이면 직접 존재하는 슬롯·객체 행·직접 소유한 slug만 읽는다. 잘못된 행은 제외하되 앞뒤 정상 주소는 유지한다. URI 인코딩 가능 여부를 포함한 기존 slug 검증을 그대로 사용한다.
- 입력 순서와 정확한 중복 제거를 유지한다. 한글·퍼센트·특수문자는 원문으로 Next에 전달하며, 재귀 디코딩·선행 인코딩·문자열 추측 변환을 하지 않는다. 원본 배열/행도 수정하지 않는다.
- **응답 자체가 목록이 아니면 오류로 중단한다.** 이를 정상 빈 배열로 바꾸어 내용이 없는 빌드를 성공시키지 않는다. 네트워크 실패도 기존처럼 호출자에게 전파한다. 모든 오류 상황에서 무조건 빌드를 성공시키는 변경이 아니다.
- 정상 빈 배열은 허용한다. 기존 `dynamicParams` 기본 동작을 유지하며 사전 생성하지 않은 정상 상세 주소는 요청 시 처리할 수 있다. 저장소 조회·공개 여부 확인은 상세 본문/메타데이터에서 계속 수행한다.

## 기준과 검증

- 설치된 Next.js의 `generate-static-params.md` 전체를 읽었다. 반환 형식은 params 객체 배열이며, 정상 빈 배열과 요청 시 생성 동작은 현재 Cache Components 미사용 구성에 해당한다. 향후 Cache Components를 활성화하면 빈 배열 정책을 다시 검토해야 한다.
- 새 회귀 테스트 **40개**: 공통 함수 20개와 실제 Works/Crew 생성기 연결 20개. 오류 분류·행 구조 경계를 포함해 수정 전 28개 실패를 확인하고 수정 후 모두 통과했다.
- 비정상 목록, `null`/빈 슬롯/상속 행, 원문 slug 보존, 읽기 전용 입력, 정상 빈 조회, 네트워크 실패 전파를 검사한다. 기존 본문/공유/사이트맵의 단일 인코딩·공개 필터 테스트도 통과했다.
- 전체 **4,871개 / 115개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 빌드 manifest에서 Works **8개**, Crew **3개** 상세 사전 생성을 집계 확인했다.
- 로컬 프로덕션 스모크 **41/41 통과**. 사이트맵의 상세 본문·공개 페이지·비로그인 관리 차단을 확인했으며 임시 서버는 종료했다.

## 범위와 한계

- 개별 행 제외는 기존 잘못된 slug 제외 정책을 확장한 것이다. 제외된 CMS 문서를 삭제/수정한 것이 아니며, 사전 생성에서 빠졌다고 문서 접근을 허가하거나 영구 404로 바꾸지 않는다.
- 현재 함수는 JSON 형태의 SDK 응답을 대상으로 한다. 임의 실행 코드가 만든 Proxy나 예외를 던지는 getter까지 안전하게 실행하는 격리 환경은 아니다.
- 잘못된 원본 응답은 모의 SDK로 검사했다. 운영 Sanity 서버를 실패시키거나 잘못된 문서를 저장해 전체 빌드 실패를 시험하지 않았다.
- 디자인·스키마·캐시 정책·의존성·환경변수·운영 저장·업로드·커밋·배포는 변경하지 않았다.
