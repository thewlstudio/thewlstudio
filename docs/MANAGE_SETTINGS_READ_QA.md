# 연락처·Studio 안내 설정 읽기 상태 점검

## 확인한 문제와 기존에 안전했던 동작

- 관리 페이지는 공개 표시용 `mergeSettings`/`mergeInfoForManage`를 사용했다. 일부 필드의 누락뿐 아니라 잘못된 자료형·필터링된 배열 행도 기본값이나 빈 값처럼 보여, 원본이 어떻게 대체됐는지 모른 채 전체 폼을 저장할 수 있었다.
- 조회 쿼리가 고정 ID와 종류를 함께 필터링해, 같은 고정 ID에 다른 종류의 문서가 있으면 실제로는 문서가 있어도 없음처럼 보였다. 저장 도우미는 이미 종류를 확인해 덮어쓰기를 거부했지만 읽기 화면에서는 최초 설정과 구분하지 않았다.
- Studio 안내의 배열 투영은 원래 필드 자료형을 그대로 보여주지 않을 수 있다. 잘못된 배열을 누락 필드처럼 판별하지 않도록 관리자 쿼리에서 원본 배열 필드를 읽을 필요가 있었다.
- **조회 예외는 이미 안전하게 상위 오류 경계로 전달되고 있었다.** 이 경우 기본값 폼을 열지 않는 기존 동작은 유지하고 회귀 테스트로 고정했다.
- 실제 관리 페이지 테스트 22개를 먼저 작성했으며 수정 전 **17개가 실패**, 정상 표시·명시적 비우기·조회 예외 등 5개는 이미 통과했다.

## 네 가지 읽기 상태

| 상태 | 판별과 화면 동작 |
| --- | --- |
| 최초 설정 | 명시적인 `null` 조회 결과. 기본값 폼과 첫 저장 시 문서 생성 안내 |
| 정상 | 고정 ID·종류·버전과 표시값 자료형이 정상. 기존 폼 유지, 추가 안내 없음 |
| 대체 표시 | 일부 값이 없음/null, 연락처의 빈 값, 안내의 누락된 하위 값. 기존 대체 규칙으로 표시하고 어떤 묶음이 대체됐는지와 저장 영향을 안내 |
| 안전하게 읽지 못함 | 비정상 응답·문서 정보·자료형·연락처 전화/서비스 URL 규칙 불일치. 편집 폼을 열지 않고 항목 이름과 원본 확인 경로 안내 |

조회 예외는 네 상태로 바꿔 삼키지 않는다. 기존 `/manage/error.tsx`의 재시도 화면으로 전달한다. `undefined` 같은 예상 밖 응답은 문서 없음으로 간주하지 않는다.

## 반영 내용

- 서버 전용 `manage-settings-read.ts`에서 원본 상태를 먼저 확인한다. 원본 값은 반환하거나 수정하지 않고 상태와 고정된 항목 이름만 반환한다.
- 두 관리자 쿼리는 고정 ID만으로 조회하고 `_id`, `_type`, `_rev`를 확인한다. 다른 종류의 문서를 없음처럼 숨기지 않는다. 문서의 종류가 다르거나 버전을 읽지 못하면 폼을 열지 않는다.
- 안내 설정은 서비스·장비·멤버십 원본 배열을 조회해 자료형과 잘못된 행을 확인한다. 폼으로 전달할 때는 기존 관리 모델을 사용하므로 알 수 없는 확장 필드를 그대로 클라이언트에 넘기지 않는다.
- 연락처는 기존 공통 전화번호·HTTPS/서비스 호스트 검사와 같은 기준을 사용한다. 잘못된 저장 링크를 기본값 링크로 조용히 바꾼 편집 화면을 열지 않는다.
- 안내의 명시적인 빈 문자열·빈 배열은 누락으로 경고하지 않는다. 필드가 없거나 null이면 기존 공개 기본값/빈 값 규칙을 유지하며 대체 안내를 표시한다. 원본 키가 없는 예전 행의 최초 발급은 기존 별도 정책으로 유지한다.
- 잘못된 자료형/배열 행은 전체 편집 폼을 열지 않는다. 일부 항목만 수정하는 사이 원본이 기본값으로 덮이는 것을 피하기 위한 보수적 UI 정책이다. 원본 확인은 기존 `/admin` 또는 개발자를 통해 처리한다.
- `SettingsReadNotice`는 최초/대체 표시를 `role="status"`, 읽기 차단을 `role="alert"`로 안내한다. 원본 값·오류 객체·인증 정보는 표시하지 않는다. 관리 도구 링크는 기존 GuardedLink와 `prefetch={false}`를 사용한다.
- 공개 페이지의 fallback/캐시/SEO 동작, 관리 저장 액션·인증·revision·고정 문서 쓰기 정책은 바꾸지 않았다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`와 `01-app/01-getting-started/04-linking-and-navigating.md`를 읽었다. 기존 내부 링크/미저장 이동 보호 테스트도 유지했다.

## 검증

새 테스트 **71개**를 추가했다.

- 상태 판별 **49개**: 두 문서의 정상/없음/식별 정보, 연락처 10개 필드의 누락·빈 값·잘못된 자료형, 전화/링크 규칙, 안내 일반 문구·배열·중첩 값·키 자료형, 항목 이름 중복 제거, 원본 불변성. 한 테스트 안에서도 여러 경계값을 확인한다.
- 실제 관리 페이지 SSR **22개**: 최초 설정·정상·대체 안내·잘못된 자료형/문서 정보의 폼 미출력, 예상 밖 응답, 조회 예외 전달, 고정 ID 조회, 원본 배열 조회, 명시적 비우기의 무경고. 폼·내비게이션·시각 컴포넌트 일부와 저장소는 모의 구현으로 대체했다.
- 기존 안내 키 조회 테스트 fixture에 실제 조회 메타데이터를 추가하고, 원본 배열 조회도 키를 반환하는 것으로 맞췄다. 키 전달 기대값이나 기존 이동 보호 규칙을 완화하지 않았다.

전체 **2,308개 / 70개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크 **35/35 통과**.

현재 공개 API의 고정 설정 두 문서를 읽기 전용으로 조회하고 실제 판별 함수를 적용했다. `siteSettings`와 `studioInfo` 모두 **정상**, 대체/차단 대상 항목 **0개**였다. 원문·식별 값·인증 정보를 출력하지 않았고 문서/에셋 쓰기도 하지 않았다.

## 범위와 한계

- 적용 범위는 `/manage/contact`, `/manage/studio/info` 두 화면이다. 목록·다른 상세 편집 화면의 모든 비정상 원본을 안전하게 다루도록 일반화한 것은 아니다.
- 이후 [상세 원본 읽기 점검](MANAGE_DETAIL_READ_QA.md)에서 강사·Crew·Works·공간 상세의 변환 전 검사도 추가했다. 목록 처리까지 완료했다는 뜻은 아니다.
- 읽기 상태에 따른 **UI 보호**다. 기존 권한 검사나 저장 API에 새 쓰기 금지 정책을 추가한 것은 아니다. 승인된 관리 도구·직접 호출의 유효한 저장을 막거나 원본을 자동 수정하지 않는다.
- 누락 필드의 편집은 계속 허용한다. 대체 표시 안내를 확인한 뒤 저장하면 보이는 기본값/빈 값도 함께 반영되는 기존 전체 스냅샷 계약이다. 누락을 모든 경우에 조회 실패나 손상으로 단정하지 않는다.
- 전화/URL 외 모든 값의 업무상 정확성·글자 수 한도·고급 키 무결성까지 읽기 상태에서 판단하지 않는다. 해당 저장 검증과 기존 키 정책은 유지한다.
- 운영 CMS 저장·인증된 운영 브라우저 E2E·새 안내의 시각/스크린리더 실기 검증·배포는 하지 않았다. 정상 운영 두 문서는 추가 안내가 없는 상태다.
- 정상 공개 디자인·운영 데이터·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
