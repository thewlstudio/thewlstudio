# 공개 페이지 검색·공유 메타데이터 점검

## 실제 확인한 문제

수정 전 로컬 프로덕션 서버의 HTML을 공유 봇 요청으로 확인했다.

- `/works`, `/crew`, `/studio`, `/class`, `/contact`: 일반 제목·설명·canonical은 각 페이지 것이지만 OG/Twitter 제목·설명은 홈페이지 것을 상속했다. `og:url`도 홈페이지 주소였다.
- 작품·Crew 상세: 제목·설명·이미지는 맞았지만 자식의 OG 객체가 부모 객체를 덮어써 `og:url`, `og:type`, `og:site_name`, `og:locale`이 없었다.
- 확인한 작품·Crew 상세의 브랜드명 중복은 없었다. 중복이 있었다고 판단하거나 그 이유로 화면 제목을 바꾸지 않았다.

설치된 Next.js **16.4.3**의 다음 문서를 읽고 구현했다.

- `node_modules/next/dist/docs/01-app/01-getting-started/14-metadata-and-og-images.md`
- `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md`의 제목·URL 조합·OG·상속/얕은 병합 규약

## 반영 내용

- `publicPageMetadata`에서 페이지별 제목·설명·정규 주소와 OG/Twitter 필드를 함께 선언한다. 하위 페이지가 OG 객체를 덮어써도 공통 필드가 빠지지 않는다.
- 기존 제목의 최종 출력은 유지한다. `title.absolute`로 이미 완성된 제목에 상위 템플릿이 다시 붙지 않도록 명시했다.
- 다섯 섹션의 기존 소개 문구를 `PUBLIC_SECTIONS`에 그대로 모았다. 새 사업 소개 문구나 디자인은 만들지 않았다.
- Works 목록의 공유 주소도 서버가 선택한 실제 페이지 번호를 사용한다. 추적 쿼리는 canonical과 공유 주소 모두에서 제외한다.
- 상세 주소는 기존 slug 검증·인코딩 결과를 그대로 사용한다. 추가 decode/encode는 하지 않는다.
- 기존 콘텐츠 이미지의 1200px 제한과 카드 유형은 유지한다. 콘텐츠 이미지가 없는 경우에만 기존 브랜드 로고와 `summary` 카드를 사용한다.
- 홈과 대체 이미지가 동일한 `PUBLIC_SHARE_IMAGE` 선언을 사용한다. 기존 파일을 직접 측정해 **839×839px**임을 재확인했다. 새 이미지를 제작하거나 업로드하지 않았다.

## 검증 결과

### 자동 테스트·빌드

- 이번에 회귀 테스트 **16개 추가**: 다섯 실제 섹션의 metadata export, 상세 OG 공통 정보, 없는 이미지의 대체 처리, 이미지 복사본, 쿼리·특수문자 주소 보존, 실제 Works 페이지 번호 반영.
- 전체 **1,156개 / 51개 파일** 통과.
- 타입 검사·ESLint·프로덕션 빌드 통과.
- 타입 검사와 빌드를 동시에 실행한 첫 검사는 빌드의 생성 파일 교체와 겹쳐 `.next/types` 누락으로 중단됐다. 빌드 완료 후 타입 검사와 ESLint를 다시 실행해 통과했다. 검증 명령은 생성 파일을 사용하는 타입 검사와 빌드가 겹치지 않게 실행하는 편이 안전하다.

### 최종 프로덕션 HTML

별도 운영 문서를 만들지 않고 최종 빌드를 localhost에서 실행했다. 사이트맵의 공개 **17개 경로**(고정 6개, 작품 8개, Crew 3개)와 Works 쿼리 변형 3개에 각각 `Twitterbot`·일반 요청을 보내 **40/40 응답**을 검사했다.

- 상태 200, 단일 제목·canonical·각 공유 태그.
- 일반 제목 = OG 제목 = Twitter 제목, 일반 설명 = OG 설명 = Twitter 설명.
- canonical과 `og:url`의 최종 주소 일치. 실제 공개 호스트 설정을 사용하며 localhost 주소로 바꾸지 않는다.
- 사이트명·한국어 locale·website 유형·이미지·카드 선언 존재.
- 봇 요청의 공유 태그는 실제 `<head>`에 위치.
- `n@di`의 `%40` 인코딩 상세 주소도 일치.
- 현재 작품은 8건이므로 범위를 벗어난 Works 페이지 번호는 `/works`로 정규화된다. 여러 페이지가 있는 경우의 `/works?page=3`은 25개 합성 데이터의 기존 페이지 테스트에서 확인했다.

기존 스모크도 **35/35 통과**했다. 공개 상세 본문, 관리 경로의 비로그인 차단, 관리 화면 noindex, 보안 헤더 검사를 포함한다.

## 범위와 한계

- 본문·CSS·탐색 동작은 변경하지 않았다. 이번 검증 대상은 서버 HTML의 메타 태그이며, 별도 브라우저 화면 캡처는 하지 않았다.
- 카카오톡/X 등의 실제 카드 렌더링이나 플랫폼 캐시는 검증하지 않았다. 배포하지 않았으므로 운영 공유 카드가 바뀌었다는 뜻도 아니다.
- 사이트맵/robots 정책, JSON-LD의 데이터 모델·날짜 표현, 검색엔진 등록·색인 상태는 이번 수정 범위에 포함하지 않았다.
- Contact의 소개는 기존 승인된 주소·교통 문구를 유지한다. CMS의 주소가 변경되는 경우 소개 문구까지 연동하는 정책은 별도 점검이 필요하다.
- 운영 데이터·환경변수·의존성·커밋·배포는 변경하지 않았다. 확인용 로컬 서버는 종료했다.
