# /manage 판매 준비 설계서 (계정·권한, 설치·인계, 운영)

목표: 지금의 /manage를 **다른 스튜디오·사업자에게 제공할 수 있는 제품**으로 만들기 위해 무엇이 부족하고 어떤 순서로 채울지 정한다.
이 문서는 설계다. 구현은 §6의 결정이 난 뒤 단계별로 한다.

## 0. 전제와 권장 방식
| 방식 | 내용 | 평가 |
|---|---|---|
| **A. 고객마다 독립 설치 (권장)** | 고객별로 코드 사본(템플릿 저장소) + 자기 Sanity 프로젝트 + 자기 Vercel 프로젝트. 데이터·장애·비용이 고객끼리 섞이지 않는다. | 현재 구조와 가장 잘 맞고 가장 빨리 판매할 수 있다. 설치·업데이트 비용이 고객 수에 비례해 늘어나는 것이 단점이라 §3의 자동화가 핵심이다. |
| B. 한 코드베이스로 여러 고객(멀티테넌트 SaaS) | 한 서비스에 여러 고객이 들어와 각자 사이트를 운영. | **비권장.** 공개 사이트 전체가 한 스튜디오 전용으로 짜여 있어(브랜드·문구·페이지 구성 §3-3) 고객별 사이트 렌더링·도메인·데이터 분리부터 새로 만들어야 한다. 판매 후 수요가 확인되면 그때 다시 검토. |

이후 내용은 A를 전제로 한다.

## 1. 현재 상태 (코드 확인)
- 인증: 공유 비밀번호 1개 + 서명된 12시간 쿠키(`lib/manage-auth.ts`). 계정·역할 없음. 실패 시 1.5초 지연만 있고 잠금 없음.
- 세션 폐기: 서버에서 개별 폐기 불가. 전체 폐기는 `MANAGE_SECRET` 교체뿐.
- 접근 확인 지점: 인증을 확인하는 파일 28개(서버 액션·페이지·라우트). 모든 변경 동작이 `requireAuth()` 한 함수를 거치므로 **권한 검사를 한 곳에 모으기 쉬운 구조**다.
- "누가 바꿨나": 기록되지 않는다. 모든 저장이 같은 쓰기 토큰으로 이뤄져서, Sanity 변경 이력만으로는 사람을 구분할 수 없다고 판단한다(이력 응답의 작성자 필드는 이번에 확인하지 않았다 — 단계 2 구현 전에 확인).
- 고객 전용 값: 브랜드·문구·페이지 구성이 코드에 박혀 있는 파일이 15개 이상(공개 화면 기준, 관리 화면·문서 제외).
- 설치: `.env.example`과 MANAGE_GUIDE 환경변수 절이 전부다. 자동화 없음.

## 2. 계정·권한 설계 (단계적)

### 2-1. 단계 1 — 공유 비밀번호 보강 (작업량 작음, 설치형이면 충분한 경우가 많다)
- 로그인 시도 제한: 실패 횟수를 저장할 곳이 필요하다. 서버리스라 메모리는 쓸 수 없으므로 **Upstash Redis 등 외부 저장소 또는 Sanity 문서 한 개**를 쓴다. (IP·시간당 5회 → 15분 잠금)
- 세션 즉시 폐기: 세션 서명 값에 `세션 버전` 번호를 넣고, 번호를 올리면 모든 기기가 로그아웃되게 한다. 번호는 환경변수가 아니라 Sanity 설정 문서에 두어 **배포 없이** 바꾼다.
- 비밀번호 변경 화면(현재 비밀번호 확인 → 새 비밀번호)은 환경변수 방식에서는 불가능하다 → 단계 2에서 해결.

### 2-2. 단계 2 — 개인 계정 + 2개 역할 (권장 목표)
**저장:** 계정 정보(이름, 이메일, 역할, 비밀번호 해시(scrypt, 솔트 포함), 활성 여부, 마지막 로그인)는 **콘텐츠가 있는 데이터셋에 두지 않는다.** 현재 데이터셋은 공개라서 토큰 없이도 모든 문서가 읽힌다(운영 데이터셋을 익명으로 조회해 확인함). 계정 문서를 같은 곳에 두면 이메일과 비밀번호 해시가 그대로 노출된다. 따라서 **별도의 비공개 Sanity 데이터셋**(또는 외부 저장소)에 `manageUser` 문서를 두고, 읽기·쓰기는 서버의 쓰기 토큰으로만 한다. 설치 체크리스트에 "계정용 비공개 데이터셋 생성"을 넣는다.
**로그인:** 이메일 + 비밀번호. 첫 계정(소유자)은 설치 때 환경변수로 만든 초기 비밀번호로 생성하고, 이후 초대 링크(만료 24시간)로 직원을 추가한다.
**세션:** 기존 서명 쿠키에 사용자 id·역할·세션 버전을 넣는다. 사용자를 비활성화하면 즉시 무효.

| 동작 | 소유자 | 편집자 |
|---|---|---|
| 강사·Crew·Works·Studio·Contact 내용 수정 | O | O |
| 새로 만들기, 비공개/공개 전환, 순서 변경 | O | O |
| 삭제(휴지통), 복원, 변경 이력 되돌리기 | O | O (휴지통 영구 삭제는 없음) |
| 홈페이지 공통 설정·연락처 변경 | O | O |
| 계정 추가·삭제·역할 변경, 비밀번호 초기화 | O | X |
| 전체 세션 폐기 | O | X |

(2개 역할이면 충분한 이유: 스튜디오 규모에서는 "관리자/직원" 구분이 필요하고, 영역별 권한은 설명·관리 비용이 더 크다. 요구가 생기면 `허용 영역` 목록을 계정에 추가하는 방식으로 확장.)

**작성자 기록 (누가 바꿨나):**
- 각 저장·삭제·복원·순서 변경 때 문서에 `lastEditedBy {userId, name}`을 같이 쓴다.
- 별도 감사 로그 문서 `manageAudit`(시각, 사용자, 동작, 대상, 요약)를 **덧붙이기만** 한다. 목록은 소유자가 변경 이력 화면에서 본다.
- Sanity 변경 이력(내용 비교·되돌리기)은 지금대로 쓰고, 이력 화면의 각 줄에 감사 로그에서 찾은 작성자를 붙인다(같은 시각대 매칭).

**코드 영향:** `requireAuth()` → `requireRole("owner"|"editor")` 또는 `requireUser()`로 교체. 28개 파일, 대부분 한 줄 변경. 계정 관리 화면 1개(`/manage/accounts`)와 로그인 화면 변경이 새 작업이다. `manage-guards.test.ts`에 "모든 변경 동작이 권한 검사를 거친다" 규칙을 추가한다(현재의 `requireAuth` 규칙을 확장).

### 2-3. 단계 3 — 외부 로그인(Google 등)
고객이 구글 계정을 쓰길 원하면 이메일 로그인 대신 OAuth를 붙인다. 단계 2의 `manageUser`와 역할 구조는 그대로 쓴다. 판매 초기에는 **하지 않는다**(설정 부담, 외부 의존).

## 3. 설치·인계 설계

### 3-1. 설치 플레이북 (사람이 하는 단계와 자동화 후보)
| # | 단계 | 담당 | 자동화 |
|---|---|---|---|
| 1 | 템플릿 저장소에서 고객 저장소 생성 | 사람 | GitHub "template repository" 기능 |
| 2 | Sanity 프로젝트·비공개 데이터셋 생성, CORS 설정, Editor 토큰 발급 | 사람 | `sanity` CLI로 일부 스크립트화 |
| 3 | Vercel 프로젝트 연결, 환경변수 입력(`MANAGE_*`, `SANITY_*`, `NEXT_PUBLIC_*`) | 사람 | `scripts/provision`이 값 목록·랜덤 시크릿을 만들어 출력 |
| 4 | 초기 문서(사이트 설정·Studio 정보·샘플 항목) 만들기 | 스크립트 | 기존 `scripts/migrate-*.ts`를 "빈 사이트 시드"로 정리 |
| 5 | 고객 브랜드·문구·로고 반영 | 사람 | §3-3 상수 모으기 후 한 파일 수정 |
| 6 | 도메인 연결, `NEXT_PUBLIC_SITE_URL` 설정 | 사람 | 없음 |
| 7 | 인수 검사 | 스크립트+사람 | `npm run smoke 주소` + 운영 5분 점검(저장·미리보기·복원) |
| 8 | 인계: 소유자 계정 전달, 사용 안내 링크, 백업·지원 안내 | 사람 | 인계 문서 템플릿 |

### 3-2. 인수 검사 표준화
- 자동: 스모크(현재 37개) + 영역별 읽기 점검.
- 수동(5분): 사진 없이 저장 / 비공개 저장 → 미리보기 → 공개 / 삭제 → 되돌리기 / 변경 이력 복원. 체크리스트를 `docs/HANDOVER_CHECKLIST.md`로 만든다.

### 3-3. 템플릿화 작업 (설치형의 전제 조건)
- 코드에 박힌 브랜드·문구·구조를 한 곳(`src/config/site.ts` 같은 파일)으로 모은다: 이름, 영문/한글 표기, 메타 설명, 공유 이미지, JSON-LD 정보, 헤더·푸터 고정 문구.
- 이 스튜디오에만 있는 페이지 구성(Class·Studio의 연습실 구조 등)은 **켜고 끄는 설정**으로 분리하거나, 처음에는 "이 구성 그대로 판매"로 범위를 고정한다. 판매 대상이 같은 업종(음악 스튜디오)이면 후자로 충분하다.
- 업데이트 배포: 템플릿 저장소에 수정을 올리고 고객 저장소가 upstream을 병합한다. 고객별 수정은 `src/config`와 콘텐츠에만 허용해 병합 충돌을 줄인다.

## 4. 운영·지원
- **오류 모니터링:** 고객 프로젝트마다 Sentry 프로젝트 1개. DSN을 환경변수로. (현재 미연결 — DSN 필요)
- **백업:** GitHub Actions 예약 작업으로 `sanity dataset export`를 매주 실행해 비공개 저장소·스토리지에 보관. 복구 리허설을 인수 검사에 포함.
- **업데이트 정책:** 보안·오류 수정은 모든 고객 저장소에 병합, 기능 추가는 고객 요청·계약에 따른다.
- **지원 범위 문서:** 응답 시간, 포함/미포함 작업, 데이터 소유(고객 Sanity 프로젝트의 소유자는 고객)를 한 장으로.

## 5. 구현 단계
| 단계 | 내용 | 검증 |
|---|---|---|
| S1 | 템플릿화: 브랜드·문구 상수 모으기, 시드 스크립트 정리 | 같은 코드로 다른 이름의 빈 사이트가 빌드·스모크 통과 |
| S2 | 설치·인계 문서와 `scripts/provision`, 인수 검사 체크리스트 | 빈 환경에서 처음부터 설치해 보기(시간 측정) |
| S3 | Sentry 연결, 백업 자동화 | 의도적 오류가 Sentry에 도착, 백업 파일로 복구 리허설 |
| S4 | 계정·권한 단계 1 (로그인 제한, 세션 폐기) | 단위 테스트, 잠금·폐기 시나리오 |
| S5 | 계정·권한 단계 2 (개인 계정·역할·작성자 기록) | 권한 규칙 가드 테스트, 편집자가 계정 화면에 못 들어가는지, 작성자 표시 |

S1~S3은 고객이 1곳이어도 필요한 최소 작업이라 먼저 한다. S4~S5는 "직원이 2명 이상인 고객"이 생기면 착수한다.

### 5-1. 진행 현황
- **S1 일부 완료 (2026-10-29):** 고객 고유 이름·설명·사이트 주소를 `src/config/site.ts`로 모았다. 헤더·푸터·히어로·소개·연락처·404·메타데이터·JSON-LD·robots·sitemap이 같은 값을 쓴다. 수정 전후 빌드 결과(HTML 18개)를 비교해 화면이 같음을 확인했고, 공개 코드에 고객 이름이 다시 박히면 실패하는 가드 테스트(`config/site.test.ts`)를 넣었다. 이름을 임시로 바꿔 빌드하면 공개 HTML에서 옛 이름이 사라지는 것도 확인했다.
- **S1 진행 2 (2026-10-29):** 고객 고유 기본 콘텐츠를 `src/config/default-content.ts`로 옮겼다(연락처·링크·홈페이지 소개 문구, 연습실·로비, 서비스·장비·멤버십·이용 안내, 네이버 지도 주소). `lib/*`는 기존 이름(`FALLBACK_*`)으로 다시 내보내서 다른 코드는 바뀌지 않았다. 이전·시드 스크립트(`scripts/migrate-*.ts`)는 **이 기본값을 그대로 Sanity 문서로 만들고**(`createIfNotExists`라 재실행 안전), 프로젝트·데이터셋은 `.env.local`/환경변수에서 읽는 공통 클라이언트(`scripts/lib/sanity-client.ts`)를 쓴다. 연습실 데이터가 스크립트와 앱에 이중으로 있던 것도 한 곳으로 합쳤다. 수정 전후 HTML 18개가 일치함을 확인했다.
  - 새 고객 흐름: `src/config/site.ts`와 `default-content.ts`를 그 고객의 내용으로 채우고 → `.env.local`에 그 고객의 Sanity 프로젝트를 넣고 → `migrate-*.ts --apply`로 문서를 만든다. 그러면 Sanity 문서와 기본값이 같아져, 조회 실패 때도 옛 고객 정보가 나가지 않는다.
- **S2 진행 (2026-10-29):** `docs/INSTALL_GUIDE.md`, `docs/HANDOVER_CHECKLIST.md`, `npm run provision -- init|check`(`scripts/provision.ts`, 로직은 `lib/provision-core.ts`, 테스트 23개)를 만들었다. `init`은 안전한 비밀번호·시크릿을 만들어 `.env.local`(권한 600, 덮어쓰기 거부)과 Vercel 입력 목록을 만들고, `check`는 값을 출력하지 않고 설치 기준을 점검한다. 기본 Sanity 프로젝트 ID도 `config/site.ts`로 모았다. **빈 프로젝트에서 처음부터 설치해 보는 시연과, 설치 가이드의 시간 측정은 아직 하지 않았다**(계정에 새 프로젝트를 만들어야 해서 사용자 확인 필요).
- **S3 일부 (2026-10-29):** 자동 백업 `.github/workflows/backup.yml`(매주, 사진 포함, 점검 후 35일 보관)과 백업 점검 `scripts/verify-backup.ts`(+ `lib/backup-verify.ts`, 테스트 10개), 복구 절차 `docs/BACKUP_RESTORE.md`를 만들었다. 점검 스크립트는 실제 운영 내보내기 파일로 확인했다. **GitHub Actions 위 실제 실행, Viewer 토큰으로 내보내기, 복구 리허설은 미확인**(시크릿 설정·시험용 데이터셋 생성이 필요). **Sentry 서버 측 연결**도 준비했다: `instrumentation.ts`(서버 렌더 오류), `lib/error-reporting.ts`(관리 화면 저장 등의 예상 밖 실패, 사용자 실수·충돌은 제외). `SENTRY_DSN`이 없으면 완전 휴면이고, 켜도 쿠키·본문·헤더·쿼리·사용자 정보는 보내지 않는다(v11 기본값이 수집이라 명시적으로 끔). 공개 페이지 번들에는 영향 없음. **실제 이벤트 도착은 DSN이 없어 미확인.**
- **S1 남은 일:**
  1. **이미지**: `public/images`의 로고·로비·연습실 사진, `About`의 사진 구성은 이 스튜디오 것이다. `migrate-studio-spaces`는 `public/`의 파일을 Sanity로 올리므로 사진도 고객 것으로 교체해야 한다.
  2. **스크립트 실행 검증**: 스크립트 수정 후 실제 실행(미리보기 모드)은 아직 하지 못했다. 이 환경에서 운영 데이터셋에 접속하는 실행이 허용되지 않아, 린트·타입 검사까지만 통과했다. 빈 테스트 프로젝트에서 처음부터 돌려 보는 것이 S2의 첫 검증이다.
  3. **페이지 구성**: About의 A~D룸 사진 5장, Studio의 연습실 구조는 "현재 구성 그대로 판매"(결정 2)로 범위를 고정한다.

## 6. 결정이 필요한 것 (권장 포함)
1. **판매 방식:** A(고객별 독립 설치) — 권장.
2. **판매 대상 범위:** 같은 업종(음악 스튜디오)에 "현재 구성 그대로" — 권장. 업종을 넓히면 §3-3 설정화 비용이 커진다.
3. **계정 수준:** 첫 고객은 단계 1(공유 비밀번호 보강), 직원이 2명 이상인 고객부터 단계 2 — 권장.
4. **계정 저장소:** 비공개 Sanity 데이터셋 — 권장(추가 서비스 없이). 단계 1의 로그인 시도 제한만 Upstash Redis 등 외부 저장소가 필요하다.
5. **오류 모니터링:** Sentry 계정·DSN 준비 필요 (사용자 작업).

## 7. 한계
- 이 설계는 한 고객당 한 사이트를 전제한다. 고객 수가 많아지면 업데이트 병합과 지원 부담이 커지므로, 그때 B안(멀티테넌트)을 다시 본다.
- 법적 사항(이용약관, 개인정보 처리 — 계정 이메일·비밀번호 해시 보관 포함)은 이 문서 범위 밖이며, 판매 전에 별도로 확인해야 한다.
- 실제 고객 설치 시간·지원 부담은 첫 고객을 설치해 봐야 알 수 있다.
