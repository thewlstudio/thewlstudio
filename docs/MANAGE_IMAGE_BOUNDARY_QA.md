# 이미지 전송·응답·원본 참조 경계 점검

## 확인한 문제

- 동일한 파일 필드가 여러 번 전송되면 `FormData.get()`이 첫 값만 선택했다. 첫 값이 미선택 파일이면 뒤에 있는 실제 선택 파일이 무시될 수도 있었다.
- Works 블록은 자료형·한도는 먼저 검사했지만, 영상 주소·크레딧 링크·오디오 제목/아티스트 검사는 재작성 도중 실행했다. 뒤쪽 오류 전에 앞쪽 이미지가 이미 업로드될 수 있었다.
- 업로드 API 응답의 `_id`를 검사하지 않아, 비정상 응답을 잘못된 참조로 저장하거나 내부 TypeError를 노출할 수 있었다.
- Works·Studio의 유지 대상 사진 참조가 읽기 이후 손상되면, 다른 필드 저장 때 사진이 자동 제외되거나 깨진 값을 재작성할 수 있었다.
- 모의 저장소에서 재현한 결함이며 운영에서 손실이 실제 발생했다는 뜻은 아니다.

## 반영 내용

- 공통 요청 검사에서 고정/동적 사진 필드의 중복을 거부한다. 미선택+선택 조합도 거부하며 첫 파일의 바이트를 읽거나 업로드하지 않는다. 기존 MIME·장당 크기·전체 요청 예산 검사도 유지한다.
- Works의 모든 영상·크레딧·오디오 필수값 검사를 사진 업로드 반복문보다 먼저 끝낸다. 오류에 입력 주소 원문을 포함하지 않는다. 허용 URL·빈 영상 제외·오디오 원본 유지 규칙은 변경하지 않았다.
- 업로드 응답은 비어 있지 않은 이미지 에셋 ID 형식(`image-` 접두사와 영숫자/하이픈)인지 확인한다. 응답이 잘못되면 기존 안전한 업로드 실패 안내로 반환하고, 문서 패치·캐시 갱신은 하지 않는다. API 원문/파일명/응답 본문은 오류나 로그에 넣지 않는다.
- 실제 Work/Studio 저장 액션에서 유지하려는 서버 원본 사진의 객체·asset·문자열 `_ref`를 업로드 전에 확인한다. 읽을 수 없으면 자동 제외하지 않고 `/admin` 확인이나 명시적인 새 사진 선택을 안내한다.
- 정상 사진은 파일 누락/미선택 시 원본 전체와 crop·메타데이터를 보존한다. URL이 해석되지 않아도 문자열 원본 참조가 있으면 유지한다. 참조 에셋을 네트워크로 매번 조회하거나 손상된 메타데이터를 임의 복구하지 않는다.
- 새 사진을 명시적으로 고르면 손상된 기존 참조도 교체할 수 있다. 기존 사진 행을 제출 목록에서 제거하는 명시적 삭제, 비어 있는 새 사진 카드 제외는 기존 계약을 유지한다.
- 참조 오류는 Works의 `blocks`, Studio의 `images`에 연결된다. 오류 뒤 입력·dirty·서버 원본과 revision을 유지하고 성공 refresh를 실행하지 않는다.

설치된 Next.js의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽고 적용했다.

## 검증

새 테스트 **59개**를 추가했다.

- 공통 업로드 13개: 여섯 파일 이름/접두사의 중복, 잘못된 API 응답 7종.
- 실제 Works 정리 함수 5개: 뒤쪽 영상/크레딧/오디오 오류 시 업로드 콜백 0회, 빈 새 사진/영상 카드 제외 유지.
- 실제 저장·생성 액션 39개: 가능한 생성/수정 경로 15개의 중복 차단, 사진 경로 8개의 비정상 응답 시 원본/캐시 유지, Work/Studio 원본 참조 오류·미선택 보존·명시적 교체·삭제 16개.
- 실제 조회 페이지→폼→액션 2개: 조회 뒤 원본 참조가 손상된 경우 입력·미저장 상태·원본 유지와 오류 묶음으로의 DOM 포커스 이동.
- 인증·저장소·라우터는 모의 구현이다. 실제 운영 저장·업로드나 인증된 브라우저 E2E 검증은 아니다.

전체 **3,540개 / 96개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 점검도 **37/37 통과**했으며 임시 서버는 종료했다.

공개 Works 8개·공간 5개를 읽기 전용으로 조회했다. 현재 Works에는 이미지 블록이 0개였으므로 해당 종류의 운영 원본 참조 검증 실적은 없다. 공간 사진 13개는 실제 원본 참조 검사에 거부 0개였다. 문서·에셋 쓰기, 원문·문서 ID·토큰 출력은 하지 않았다.

## 범위와 한계

- 새 사진 카드에 파일이 없는 경우 선택하지 않은 것인지 전송에서 누락된 것인지 구분하는 새 업로드 의도 프로토콜은 추가하지 않았다. 비어 있는 새 카드는 기존대로 제외한다.
- 입력 검사를 통과한 뒤 실제 업로드 중 연결 실패나 최종 revision 충돌이 발생하면 이미 업로드된 일부 에셋은 남을 수 있다. 잘못된 API 응답 역시 서버 측 업로드까지 취소됐다는 뜻은 아니다. 에셋 자동 삭제·롤백은 하지 않는다.
- 요청의 모든 미사용/오타 파일 필드를 해당 카드와 결합해 거부하는 새 허용 목록이나 에셋 존재/권한 검사를 추가하지 않았다.
- 공개 디자인·스키마·환경변수·의존성은 변경하지 않았다. 운영 데이터 저장·실제 업로드·커밋·배포도 하지 않았다.
