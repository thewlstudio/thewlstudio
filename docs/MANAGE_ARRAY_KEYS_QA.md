# 관리자 배열 식별 키 점검

## 재현한 문제

- Works·Crew 본문과 Studio 가격의 서버 키 함수가 기존 `_key`를 앞 40자로 잘랐다. 앞부분이 같은 서로 다른 긴 키는 저장 과정에서 같은 키로 변했다. 이는 사진·항목 정체성 보존과 충돌한다.
- Works 블록·중첩 트랙·크레딧, Crew 섹션·음반·경력 등에서 같은 배열의 중복 키를 미리 거부하지 않았다. 임시 사진 키가 중복되면 같은 업로드 입력을 여러 번 참조할 수 있었다.
- Studio 사진·가격, Crew 링크도 중복 키를 그대로 조립했다. Crew 링크 키에는 `.trim()`이 있어 원본 키와 달라지면 기존 아이콘 메타데이터 조회가 실패할 수 있었다.
- 먼저 회귀 테스트 14개를 작성했으며 수정 전 모두 실패했다. 실제 Sanity가 중복 키 문서를 받아 저장하는지까지 검증한 것은 아니다. 앱이 잘못된 payload를 만들거나 업로드까지 수행하는 경로를 재현했다.

## 반영한 정책

- 서버 공통 도우미 `manage-array-keys.ts`에서 기존의 비어 있지 않은 문자열 키를 그대로 유지한다. 40자 자르기·앞뒤 공백 제거를 하지 않는다. `new-` 임시 키와 미지정 키에는 기존처럼 서버 UUID 일부를 발급한다.
- 같은 배열에 같은 키가 두 번 있으면 저장을 거부한다. 임의 삭제·병합·키 재발급으로 원본의 사진 연결을 추측하지 않는다.
- 유일성의 범위는 **같은 배열의 형제 항목**이다. 서로 다른 크레딧 묶음의 항목이나 별도 연도에 속한 트랙이 같은 키를 쓰는 것은 허용한다. 문자열 목록에서 같은 문구가 반복되는 것도 키 중복이 아니다.
- Works·Crew는 기존 본문 길이/개수 사전 검사 경로에서 최상위와 편집 가능한 중첩 객체 배열의 키를 함께 검사한다. Works에서는 뒤쪽 중첩 배열이 잘못돼도 앞쪽 사진을 업로드하지 않는다.
- Studio 저장·생성은 가격과 사진 키를 업로드 전에 검사한다. 오류 요약은 해당 그룹의 첫 입력 ID를 가리킨다.
- Crew 저장·생성은 모든 링크 키를 먼저 검사한다. 뒤쪽 키가 중복이어도 앞쪽 링크 아이콘을 업로드하지 않는다. 링크 수는 0~10의 안전한 정수만 받는다. 소수·음수·비정상 값·한도 초과 값을 조용히 자르거나 반복 범위가 다르게 해석되도록 두지 않는다.
- 인증·문서 종류 검사·revision 조건·정상 저장의 캐시 갱신은 유지한다. 기존 링크 아이콘의 에셋·crop·hotspot 보존 정책도 유지한다.
- 오류 후 기본 정보·본문·dirty 상태를 유지한다. 안내대로 내용을 따로 보관한 뒤 새로고침하거나, 기존 데이터 자체에 문제가 있으면 개발자가 원본을 확인해야 한다. 자동 새로고침은 하지 않는다.

설치된 Next.js 16.4.3의 `node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-server.md`를 읽었다. 클라이언트로 서버 전용 도우미나 인증 정보를 노출하지 않았다.

## 검증

새 테스트 **59개**를 추가했다.

- 모델·공통 규칙 **38개**: 중복 블록/섹션·중첩 배열·임시 사진 키, 공통 40자 접두사를 가진 긴 키의 무변경 왕복, 프로토타입 이름의 키, 원본 공백 보존, 키 미지정·문자열 목록, 배열 간 독립 범위, 오류 후 입력 불변성.
- 실제 저장 액션 **16개**: 중복 시 업로드·패치·캐시 없음, 잘못된 링크 수 거부, 긴 키 사진의 재정렬 후 두 번 저장과 에셋/crop 보존, Studio 긴 가격 키·Crew 원본 링크 키와 아이콘 메타데이터 보존. Sanity는 모의 저장소로 대체했다.
- 실제 생성 액션 **3개**: Crew 링크·Studio 가격/사진 중복 시 업로드·문서 생성·페이지 이동·캐시 갱신 없음.
- 실제 폼 DOM **2개**: Studio 가격·Crew 링크 오류 후 입력과 dirty 유지, 오류 요약이 존재하는 입력을 가리키고 클릭 시 포커스 이동, 자동 새로고침 없음. 오류 응답은 실제 공통 키 검사와 모의 액션으로 구성했다.

전체 **1,655개 / 60개 파일**, 타입 검사·ESLint·프로덕션 빌드 통과. 로컬 프로덕션 경로 스모크 **35/35 통과**.

현재 초안·휴지통을 제외한 공개 **Works 8건·Crew 3건·공간 5건**을 읽기 전용으로 확인했다. Works·Crew는 실제 편집 모델 왕복과 서버 정리 함수를, Crew 링크·공간 가격/사진은 공통 키 검사를 적용했다. 거부 **0건**, 새 업로드 **0회**. 문서 원문과 인증 정보는 출력하지 않았다.

## 한계와 후속 점검

- 운영 CMS 쓰기·실제 인증 브라우저 저장 E2E·배포는 하지 않았다. 모의 저장소 검증은 Sanity의 모든 키 형식/길이 규칙을 보장하지 않는다. 이번 정책은 기존 키를 불필요하게 변형하지 않는 것이며 새로운 키 문자 규칙을 만든 작업은 아니다.
- 기존 `new-` 임시 키 네임스페이스와 UUID 일부 발급 방식은 유지했다. 입력 중복 검사가 UUID의 이론적 충돌 가능성까지 제거하는 보장은 아니다.
- 편집하지 않는 자유서식·예전 섹션의 내부 배열은 재작성하거나 검사하지 않는다. 최상위 제출 배열의 중복 키는 거부하지만 모든 CMS 문서를 재귀 정리하는 마이그레이션은 아니다.
- 기존 데이터에 중복 키가 있으면 수정 저장이 차단될 수 있다. 원본을 확인해 수동 복구해야 하며, 조회·빌드 시 자동으로 키를 바꾸지 않는다. 현재 읽기 전용 검사 대상 16건에서는 발견되지 않았다.
- **후속 점검:** 이 점검 당시 남아 있던 Studio의 일반 텍스트·가격·목록 초과분 잘림은 이후 [Studio 저장 한도 점검](STUDIO_CONTENT_LIMITS_QA.md)에서 수정했다. 이 문서의 테스트 수는 키 점검 당시 기준이다.
- 정상 콘텐츠 디자인·운영 문서·에셋·스키마·환경변수·의존성·커밋·배포는 변경하지 않았다.
